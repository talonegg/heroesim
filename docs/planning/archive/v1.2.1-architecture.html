Problem. Today form is one number per Hero; v1.2.1 needs four factors, two of them per Stat area, and the scalar is read in check, preview, resolve and ~20 operator rows.

Solution. One module works out each member's formed Stats in queryParty (the only place members are built); statOf reads formed instead of multiplying; formDecided compares formed against raw.

  • Operator signatures unchanged
  • Area factors in one place
  • Tests hit one interface
  • Captain and later Traits plug in
ADR-0006 holds: the areas come from content's stats.json; StatArea is already a closed union mirrored in config-check, so per-area settings validate with each(statAreas).

2 · A Quest clock: the Day each Encounter falls on, shared by the resolver and the estimate

Strong in-process

engine/src/pipeline.ts:54-56 · phases/hero-state.ts:54,77-112 · quest-engine/resolve.ts · quest-engine/estimate.ts:165-288 · document.ts:434-458

Before — the resolver reads end-of-Quest State

sequenceDiagram
  participant N as Nights 1..n (heroState)
  participant Q as Return night: questsConclude
  N->>N: drift every night, away Heroes too
  Q->>Q: resolve all Encounters at once
  Note over Q: reads stored State = value after the last night, not "on its Day"

After — a pure clock, one rule for both

flowchart LR
  D[Party: Fatigue at dispatch] --> K
  K["Quest clock: dayOf(encounter i), fatigueOn(day)"]
  K --> R[resolve]
  K --> E[estimate: one Party per Day]
  classDef deep fill:#0f172a,color:#f8fafc,stroke-width:3px;
  class K deep

Problem. Nothing in the Quest Engine knows Days, and it resolves on the return night after every nightly step has already run, so "Fatigue on the Encounter's Day" cannot be read from the Hero.

Solution. The Party keeps each Hero's Fatigue at dispatch; a small pure module maps an Encounter's index to its Day and the Fatigue on it; the night applies the rise only to the stored figure.

  • Estimate and resolve agree exactly
  • No replay of nights
  • One rule, one test file

5 · Roles declared in content: who relieves the hurt, which Stat makes a Captain

Strong in-process

content/classes.json · content/stats.json · content/src/kinds/ · engine/src/config-check.ts:36-40 (rules never read content, DL-193)

Before — the tempting shortcut

if (hero.classKey === 'healer') …
stats['leadership']

Names a Class and a Stat in the engine; config can't validate either key.

After

classes.json: "healer": { …, "relievesHurt": true }
stats.json: "leadership": { …, "captaincy": true }

Content's own check refuses zero or two captaincy Stats; the engine reads roles.

Problem. The Healer relief and the Captain's Leadership scaling read content keys the engine must not name (ADR-0006).

Solution. A role flag on the Class and on the Stat, checked by the content kinds; the Contribution module reads the role.

  • ADR-0006 kept
  • Validated by content check
  • New Classes opt in
