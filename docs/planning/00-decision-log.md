# Decision log

Significant decisions taken during the build, recorded before or alongside implementation. Append a new entry; never edit an accepted one — supersede it with a later entry that names it. Architecture decisions taken during the design session live in [`../adr/`](../adr/) and are not repeated here.

Format: `## DL-nn — title`, then Status, Date, Context, Decision, Consequences.

---

## DL-01 — A web front end is in scope, as a second renderer over the same engine

**Status:** Accepted · **Date:** 2026-09-19

**Context.** The design is terminal-first and says workspaces arrive "when a second front end actually exists, not before". The build goal set on 2026-09-19 requires the finished game to be verified by browser testing across mobile, tablet and desktop views. A terminal program cannot be verified that way; a browser front end can. ADR-0001 and ADR-0002 already anticipate a graphical client that renders the same event stream.

**Decision.** Add an epic, **E8 — Web front end**, delivering a responsive browser client built with Vite and React that runs the engine in the browser, uses the same narration layer as the CLI, and stores saves in the browser. The terminal CLI remains the reference front end and is built first (E1-S6). The repository becomes npm workspaces now, because the second front end now exists.

**Consequences.** Narration is a shared package so both front ends say the same thing. Content (Vignettes, Traits, names) must be loadable without Node file I/O. The web client adds Vite, React and Playwright as development dependencies; it adds no running cost and no external service.

## DL-02 — Saves are JSON snapshots; the CLI writes files, the web client writes browser storage

**Status:** Accepted · **Date:** 2026-09-19

**Context.** INPUTS-REQUIRED §1.3 offered JSON, TOML or plain text with JSON as the default. ADR-0004 fixes snapshots over replay.

**Decision.** The engine exposes `serialiseCareer(career): string` and `deserialiseCareer(text): Career`, producing a JSON document with a top-level `formatVersion`. The CLI stores slots at `.career/<slot>.json` (gitignored). The web client stores the same document in `localStorage` under `heroesim.career.<slot>`. The RNG state is part of the snapshot so a loaded Career continues on the same random path as an unsaved one.

**Consequences.** One serialiser, two storage adapters. No migration is attempted; a save whose `formatVersion` does not match is rejected with a clear message, as the design permits.

## DL-03 — Vignettes and other content are TOML files in a `content` package; conditions and consequences are data

**Status:** Accepted · **Date:** 2026-09-19

**Context.** E1-S2 proposed TOML "or JSON if TOML feels heavy". The E1 skeleton sketched `conditions` and `consequences` as TypeScript functions, which cannot live in a content file. The epics definition of done placed Vignettes under `engine/src/vignettes/`, but the engine must not read files and the web client must bundle them.

**Decision.** Content lives in `content/` as TOML: `content/vignettes/*.toml` (one Vignette per file), `content/traits.toml`, `content/spheres.toml` and `content/names.toml`. Vignette conditions, slot rules and consequences are declarative data validated by the engine at load. The `content` package parses TOML text into typed objects with `smol-toml`; it has a pure entry (text in, objects out) used by the web bundle and a Node entry that reads the directory for the CLI. The engine receives parsed content and never sees a file.

**Consequences.** Adding a Vignette is adding a file. The set of consequence kinds is a small closed vocabulary owned by the engine; a new kind is an engine change, a new Vignette is not. This supersedes the location given in the epics README definition of done.

## DL-04 — Verification: engine API contract tests in Vitest; browser tests with Playwright on Chromium at three viewports

**Status:** Accepted · **Date:** 2026-09-19

**Context.** The build goal requires "API testing" and "Chrome plugin browser testing including mobile, tablet and desktop views". The engine has no HTTP surface by design; its API is its exported functions. No Chrome MCP tool is connected in the build environment; Playwright 1.63 is.

**Decision.** "API testing" is a dedicated contract suite, `engine/tests/api.test.ts`, that exercises the public surface: determinism from seed, input immutability, serialise round-trip, typed rejection of invalid calls, and full-Career smoke runs across many seeds. The CLI gets a scripted end-to-end test that drives the real process over stdin. Browser testing uses Playwright driving Chromium with three projects: mobile (Pixel 7), tablet (iPad Mini) and desktop (1280×800), asserting layout, no horizontal overflow, tap-target size and a playable journey, and capturing screenshots as evidence.

**Consequences.** If a Chrome-specific tool becomes available later the same specs can run against it; the assertions do not depend on the driver.

## DL-05 — Package layout: engine, content, narrate, cli, web

**Status:** Accepted · **Date:** 2026-09-19

**Context.** Follows from DL-01 and DL-03.

**Decision.** Five npm workspaces at the repository root:

| Package | Purity | Job |
| --- | --- | --- |
| `engine` | pure, no dependencies | world state, rules, Checks, Beats, events, serialisation |
| `content` | pure entry + Node entry | TOML text → typed content; the content files themselves |
| `narrate` | pure | events + world + content → English paragraphs |
| `cli` | Node | terminal front end, file saves |
| `web` | browser | React front end, browser saves |

ESLint forbids `engine` from importing any other workspace and forbids `Math.random`, `Date.now` and `new Date()` inside `engine` and `narrate`.

**Consequences.** The engine's only inputs are a seed, content and player decisions. Everything a test needs is constructible in memory.

## DL-06 — E1 balance defaults adopted from INPUTS-REQUIRED; a year is 360 Days

**Status:** Accepted · **Date:** 2026-09-19

**Context.** The design leaves the numbers open. The owner has not overridden the defaults offered in INPUTS-REQUIRED.

**Decision.** `GameConfig` defaults: Career 20 years; a year is 360 Days (12 months of 30); Board refreshes every 10 Days; Upkeep 50 coin every 10 Days; starting coin 500; Board holds 4–6 Commissions; Commission fees 80–200 coin by difficulty; a Commission runs 5–10 Days with 3–5 Beats; Check DCs 8–15; Stats 1–5; d20 Checks with critical at DC+5; one Rival takes one unclaimed Commission per refresh. Insolvency is coin below zero at two consecutive Upkeeps. Every number is a named field on `GameConfig`, overridable per Career and stored in the save.

**Consequences.** Balance is tuned by changing config, not code. The starting debt mentioned in the design is deferred to E7 polish; E1 starts at the configured coin with no debt.

## DL-07 — The RNG is a seeded xoshiro128** whose state is part of the Career

**Status:** Accepted · **Date:** 2026-09-19

**Context.** ADR-0001 requires injected randomness; E1-S7 requires a loaded Career to behave identically to an unsaved one.

**Decision.** The engine implements a small xoshiro128** generator seeded by hashing the seed string. Its four 32-bit words live on the Career and are serialised with it. Engine functions are pure: each takes a Career and returns a new Career plus events, never mutating its input.

**Consequences.** Same seed and same decisions give the same story on any machine. Tests can assert exact event sequences.

## DL-08 — Beat narration templates are content; the engine emits identifiers, the narrate package fills slots

**Status:** Accepted · **Date:** 2026-09-19

**Context.** ADR-0002 forbids prose in the engine, yet Vignettes carry narrative templates.

**Decision.** A `BeatResolved` event carries the Vignette id, the outcome and the resolved slot bindings (hero id, patron id, sphere id, trait name). The narrate package looks up the Vignette's template for that outcome and fills tokens such as `{hero}`, `{hero.they}`, `{patron}`, `{sphere}` and `{guildmaster}` from the world snapshot. Heroes carry pronouns so templates read correctly.

**Consequences.** Engine tests never see a sentence. Rewording a Vignette changes no test.

## DL-09 — E1 additions to the engine contract: Commission tags, a Party score, a bounded record of finished work, the rule and world-generation constants on `GameConfig`, and Injuries that lift

**Status:** Accepted · **Date:** 2026-09-19

**Context.** Building E1 against [solution architecture](03-solution-architecture.md) §2–§8 turned up five places where the contract is silent but the code cannot be. Vignette selection matches on "the Commission's tags" (§5) and the `Commission` in §3 carries none. Commission score accumulates across Beats and from `score` consequences, and `Party` in §3 has nowhere to hold it. A committed Commission leaves the Board and its Party is removed on return, so `commissionById` — and therefore `narrate`'s `{commission}` token — would have nothing to resolve. §5 states several balance numbers as literals (±1 Patron Regard, +1 Rival Standing, the −4 posting floor, the d20, the 5..20 DC clamp, the ×10 Standing scale) and world generation needs a dozen more (Stat totals, starting Regard bands, how many bonds), while CLAUDE.md invariant 8 makes a balance literal in rules code a defect. And `TraitLifted` is in the E1 event union while the rule that fires it is deferred to E3, which over twenty years leaves every Hero permanently carrying every Injury they ever took.

**Decision.**

1. `Commission` gains `tags: string[]`, copied from the Sphere's entry for that title. Vignette selection reads them from there.
2. `Party` gains `score: number`, the Commission's running score, reported on `PartyReturned`.
3. `Party` gains `commission: Commission`, the record itself, and `Career` gains `recentCommissions: Commission[]` — the last `config.recentCommissionsKept` (24) finished Commissions, newest first. `commissionById` searches the Board, then Parties, then that list. Bounded, so a save stays small.
4. `GameConfig` gains named fields for every remaining rule constant and every world-generation number, defaulted to the values §5 and this epic state. The §3 fields keep their DL-06 defaults unchanged.
5. An Injury whose `liftsOn` has arrived is removed at the start of the Day and reported with `TraitLifted`. Giving a Trait somebody already holds extends the span rather than duplicating it. E3 still owns the infirmary, the Hall and everything else about Injuries.

**Consequences.** All five are additions: no existing field changes shape and no event member changes (ADR-0002's rule that later epics only add still holds). `narrate` can resolve `{commission}` for any Beat or return in the events of a call. Balance is tuned by editing `defaultConfig`, which the E1 contract suite's retirement-rate assertion is allowed to drive; it did not need to. Under the automatic policy the defaults as written reach Retirement on all two hundred seeds of the contract suite's fixture world, and on 188 of two hundred over the authored content, the other twelve ending in insolvency.

## DL-10 — All three browser projects run on Chromium; the tablet is an iPad-class viewport, not WebKit

**Status:** Accepted · **Date:** 2026-09-19 · **Supersedes:** the "iPad Mini" wording of [DL-04](#dl-04--verification-engine-api-contract-tests-in-vitest-browser-tests-with-playwright-on-chromium-at-three-viewports)

**Context.** DL-04 fixed three Playwright projects — mobile, tablet and desktop — and named the tablet one "iPad Mini". In Playwright's device registry `devices['iPad Mini']` carries `defaultBrowserType: 'webkit'`, so taking that device literally pulls in a second browser engine. The owner's stated requirement is Chrome-engine browser testing across mobile, tablet and desktop views; a WebKit run is neither asked for nor verifiable against that requirement, and it doubles the browser download on a machine that has no need for it.

**Decision.** All three projects run on Chromium. The tablet project is an iPad-class **viewport** on Chromium — 820×1180 at `deviceScaleFactor: 2`, with `isMobile` and `hasTouch` set — rather than the iPad Mini device descriptor. `mobile` stays `devices['Pixel 7']` and `desktop` stays Desktop Chrome at 1280×800. WebKit is not installed and is not run.

**Consequences.** What DL-04 set out to prove — the three layouts, no horizontal overflow, tap targets, the journey — is proved on the engine the owner uses, at the widths that matter. The assertions still do not depend on the driver, so a WebKit or a Chrome-MCP run can be added later without touching a spec. Safari-specific rendering is not covered by this suite, and nothing in the client is written against a WebKit quirk; if the game is ever shown on an iPad this is the gap to close first.

## DL-11 — An ended Career is an empty Step from `advance`, a rejection from `commitParty`; and `deserialiseCareer` refuses a document it can only half-believe

**Status:** Accepted · **Date:** 2026-09-19

**Context.** Independent verification of the E1 engine turned up two places where the contract in [solution architecture](03-solution-architecture.md) §6 and §8 is silent and the code had to choose. First, §6 lists `CareerEnded` as one of `commitParty`'s rejections and says nothing about what the two advancing calls do once a Career has ended; `advance` and `advanceUntilAttention` both return an empty `Step`. Second, §8 says `deserialiseCareer` "checks the structural shape", and the check stopped at the outside of `ended.reckoning`: a save whose reckoning was a table but not a reckoning loaded without complaint and then threw a `TypeError` out of `cloneCareer` on the next call — a half-world let in at the boundary and blowing up somewhere else.

**Decision.**

1. Advancing an ended Career is not an error. `advance` and `advanceUntilAttention` return `{ career, events: [] }`, and the two agree; `commitParty` alone throws `EngineError('CareerEnded')`, because it is a decision the world can no longer honour and a front end must be told. Time passing over a finished Career is a no-op a front end may poll without a `try`.
2. `deserialiseCareer` validates the whole of `ended.reckoning`, including `guildmasterStats.start` and `.end` and the optional `favouritePatron`, and refuses a value outside its union for `pronouns`, a Regard's `nature`, an entry of `beatsResolved` and `ended.reason`, as well as a `liftsOn` that is not a number and a non-string entry in `tags`, `heroIds`, `vignettesUsed` or `hall`. The two answers a save may get are a `SaveError` naming the field, or a Career the engine can go on using. Never a `TypeError` two calls later.

**Consequences.** Both are pinned by tests: `engine/tests/loop.test.ts` holds the empty-Step rule beside the `commitParty` rejection, and `engine/tests/save.test.ts` corrupts every one of the four hundred-odd paths through a fully populated save seven ways each and requires a `SaveError` or a Career that still advances. The save format is unchanged and `formatVersion` stays 1 — nothing this engine ever wrote is now refused, only documents that were already malformed. A front end that stores its own extra keys alongside a Career is still tolerated: unknown fields are not rejected, but the engine drops them on the next call, so a front end must keep its own state in its own document.

## DL-12 — The narration contract: a `commit` Paragraph, a `partyId` that groups a report, strict Day order, and two flags that let the CLI be driven by a file

**Status:** Accepted · **Date:** 2026-09-19

**Context.** Building `narrate` and the CLI against [solution architecture](03-solution-architecture.md) §9 turned up three places where the sketch there cannot be taken literally. §9 gives `Paragraph = { kind: 'beat' | 'return' | 'board' | 'coin' | 'end' | 'note'; text; day }` and says narration "groups a Party's Beats and its return into one report". A Party is committed on one Day and its Beats fall on later ones, so a report cannot be one contiguous block without reordering paragraphs out of Day order — and Day order is what makes a stretch of advanced Days readable. `PartyCommitted` also has no kind in that list, yet it is the one event that reports a decision the player just made. Separately, §9 says the CLI uses `node:readline`, which cannot be driven by a test without a pseudo-terminal, while DL-04 requires "a scripted end-to-end test that drives the real process".

**Decision.**

1. `Paragraph` gains a seventh kind, `commit`, for `PartyCommitted`, and an optional `partyId`. `narrateEvents` returns paragraphs in the order the events happened, which is Day order and never anything else. A report is the paragraphs sharing a `partyId` — its Beats, the notes attached to them, and the `return` that closes it — so both front ends can group a report without either of them reordering time.
2. Accounting events never get a paragraph of their own. A coin movement from a fee or a Consequence is folded into the `beat` or `return` that caused it; a Regard movement and a Trait given or lifted fold into one short `note` carrying the Day it happened on and, where it belongs to one, the `partyId`; `ConsequenceApplied` is silent, because the movement it announces arrives as its own event with the clamping applied, and a score change is already told by the Beat.
3. The CLI takes `--script <file>`, which reads commands from a file one per line instead of from the terminal, and `--quiet`, which drops the Board redraw between commands so that only the narration is printed. They are the seam the end-to-end test drives, and they are the same code path as a terminal session — the only difference is where a line comes from.

**Consequences.** This supersedes the `Paragraph` shape in §9 and nothing else; it is an addition, so a front end that switches on the six kinds §9 lists still compiles and merely ignores `commit`. The Day-order guarantee is pinned by `narrate/tests/stream.test.ts` over a real one-year Career, and the report grouping by an assertion that every `return` shares its `partyId` with at least one earlier `beat`. The CLI's end-to-end test spawns the real process with `node --import tsx`, so nothing in the loop is mocked, and the two flags are ordinary flags a player may also use.

## DL-13 — The E1 balance pass: Commission score counted once, a wider critical margin, Patron Regard that recovers, and an economy where coin is tight

**Status:** Accepted · **Date:** 2026-09-19 · **Supersedes:** the Upkeep, fee and critical-margin lines of [DL-06](#dl-06--e1-balance-defaults-adopted-from-inputs-required-a-year-is-360-days) — "Upkeep 50 coin every 10 Days", "Commission fees 80–200 coin by difficulty" and "critical at DC+5" — and the "188 of two hundred over the authored content" figure in DL-09's consequences

**Context.** DL-06 adopted the INPUTS-REQUIRED defaults unplayed, and E1 shipped without anyone measuring what twenty years of them felt like. An independent verification of 500 seeds × 20 years under the automatic policy over the real authored content found one defect and three balance failures, and a measurement harness reproduced every one of them at 300 seeds:

| | Before |
| --- | --- |
| retirement rate | 93.7% |
| final coin, mean / median | 152,941 / 196,185 |
| Beat mix (failure / success / critical) | 29.5% / 24.9% / 45.5% |
| mean margin over DC | 3.61 |
| Patrons at or below the −4 posting floor at year 20 | 73.1% |
| Board refreshes that left the Board empty | 20.8% |
| fee income against Upkeep, per year | 9,548 against 1,800 (5.3×) |

1. **The Commission score was counted twice (F9).** The engine adds `scoreCritical`/`scoreSuccess`/`scoreFailure` per Beat *and* every one of the thirty authored outcomes carried an identical `{ kind = "score", delta = … }` consequence, so every Beat was worth twice what the rule says. A Commission of three Beats cleared its threshold on one good Beat.
2. **Criticals were the common outcome (F8).** 45.5% of Beats were critical against 24.9% ordinary successes, which flattens the Check: the band between "it worked" and "it went perfectly" barely existed.
3. **Patrons ratcheted down into silence (F6).** Every refresh docked one Patron a point for work the Roster was never large enough to take, gains were wasted against the +5 clamp, and four Heroes can only cover about two of the four to six postings. By year 20 three Patrons in four had gone quiet and one refresh in five posted nothing at all — a death spiral, and the largest threat to the game staying interesting.
4. **Coin was never a decision (F7).** Income ran at five times Upkeep and insolvency was unreachable after year two, against the design's "Coin is tight".
5. Two smaller defects: `{trait}` could be admitted where the Hero the slot resolved to need not hold it (F11), and `deserialiseCareer` returned the parsed document as a `Career`, so a front end's extra keys survived until something else happened to clone it (F13).

**Decision.**

1. **The per-Beat increment is the rule; content adds score only for the exceptional (F9).** All thirty `score` consequences are removed from `content/vignettes/*.toml` and from the engine's test fixture. The `score` consequence kind stays supported and is pinned by a test of its own, so an authored outcome can still be worth more than its result — it simply is not how ordinary Beats are scored. This is what solution architecture §5 already said; §4's illustrative TOML block still shows the doubled form and should be read as illustration rather than as a pattern to copy.
2. **`criticalMargin` 5 → 9 (F8).** Nothing else about the Check moves: Stats generation, DCs and the difficulty pivot are untouched. Eight was tried first, as the verification suggested, and left criticals at 29.4% — outside the 15–25% target; nine puts all three bands inside it without shifting a single DC.
3. **A Patron's disappointment fades (F6a).** New `patronRegardRecoveryEveryDays` (60): a Patron whose Regard for the Guild is negative recovers one point towards zero every sixty Days, reported as `PatronRegardChanged` with reason `"time passed"`. Regard at or above zero is untouched — goodwill is earned, and its decay belongs to E2. Zero switches the rule off, which is how the two "nobody will post" tests hold their world still.
4. **Being passed over never silences a Patron (F6b).** New `patronPassedOverAboveRegard` (−3): the `patronRegardOnPassedOver` dock applies only while that Patron's Regard is strictly above it. The guard sits one point above the posting floor, so no Patron can be argued into silence by work they were never asked for. Failing a Patron's own Commission still docks them without limit, so a Sphere can still be lost — by failing its Patron, which is the only way it should be losable.
5. **The economy is rescaled so that coin is a decision (F7).** `upkeepPerHero` 12 → 20 and `upkeepBase` 2 → 8, so a four-Hero Roster owes 88 every ten Days rather than 50; `feeMin` 80 → 45 and `feeMax` 200 → 115. Failure still pays nothing. Fee income now runs at 1.6× Upkeep rather than 5.3×, and the starting 500 coin is about six Upkeeps of runway.
6. **`{trait}` is admitted only when the slot and the condition agree (F11).** `validateContent` now requires both a `with_trait:X` Hero slot *and* a `conditions.requiresTrait` naming the same `X` before a narrative may carry `{trait}`. Neither alone keeps the promise the prose makes: the slot falls back to any Party member when nobody holds `X`, and the condition only says that *somebody* in the Party does. The validator route was taken rather than dropping the binding in the engine because `narrate`'s `fillTokens` throws a `NarrationError` on an unfilled token, which would turn a wrong sentence into a crash. Alongside it, `fillHeroSlot` reports a slot Trait only when the Hero it resolved to actually holds it, so `BeatResolved.slots.trait` never names a Trait its Hero lacks either.
7. **`deserialiseCareer` returns `cloneCareer(parsed as Career)` (F13).** Unknown fields are dropped at the boundary, deliberately and in one place, rather than riding along until the next call. This narrows the timing of DL-11's "the engine drops them on the next call" to "the engine drops them on load"; nothing a front end may legitimately keep in its own document changes.

**Consequences.** Measured over 300 seeds × 20 years under the same automatic policy, after all of the above:

| | Before | After | Target |
| --- | --- | --- | --- |
| retirement rate | 93.7% | 87.0% | at least 80% |
| final coin, mean / median | 152,941 / 196,185 | 29,720 / 30,430 | low tens of thousands |
| Beat failure | 29.5% | 29.9% | 25–35% |
| Beat success | 24.9% | 44.9% | 40–50% |
| Beat critical | 45.5% | 25.2% | 15–25% |
| mean margin over DC | 3.61 | 3.53 | — |
| Patrons at or below the floor at year 20 | 73.1% | 14.2% | under 25% |
| refreshes that left the Board empty | 20.8% | 0.6% | under 5% |
| fee income against Upkeep, per year | 9,548 / 1,800 | 5,100 / 3,168 | Upkeep must bite |
| Commissions taken per year | 76.1 | 95.5 | — |
| Commissions that succeed | 81.7% | 62.5% | — |

A Guildmaster who sends one weak Hero alone at the hardest work on the Board fails about half of the first two years' Commissions and goes insolvent on all 100 seeds, at a median of Day 120: insolvency is reachable again, which the design says is the only way to lose. Under the automatic policy nearly every insolvency falls inside the first two years, so the opening is where a Career is now lost and the 500 starting coin is the whole of the buffer. That is deliberate, and E3's Hall and E4/E5's Transfers will add sinks rather than relief; if the opening proves too sharp to play, `startingCoin` is the dial to turn, not the fee scale.

The measurement is committed as `content/tests/balance.measure.test.ts`, skipped unless `HEROESIM_BALANCE` is set, so the next balance pass starts from these numbers rather than from a fresh argument; `HEROESIM_BALANCE_CONFIG` takes `GameConfig` overrides, so a candidate default is measured before it is adopted. `engine/tests/api.test.ts` keeps its assertions unchanged — the fixture world still retires on 198 of 200 seeds — and two Check assertions in `check.test.ts` are rewritten off `config.criticalMargin` rather than off the number it happened to hold, which is what they should have said from the start. INPUTS-REQUIRED §2 carries the changed defaults.

## DL-14 — The E2 rules as built: Backing gains its Regard term, and a Hero at the bottom of the scale is talked round before they are lost

**Status:** Accepted · **Date:** 2026-09-19 · **Decided by:** an agent, under the owner's standing instruction to build E2 to the adopted defaults in [E2 §3](epics/E2-refusals-and-regard.md#3-known-unknowns--adopted-defaults) and to record what the plan left open · **Amends:** the Backing line of [solution architecture §5](03-solution-architecture.md#5-rules), which said "Regard does not yet contribute (E2)"

**Context.** [E2](epics/E2-refusals-and-regard.md) promised four things the contract could not state until they were built: Backing's third term, the price of insisting, what drift costs, and when a Hero walks out. Three of them are arithmetic the epic already fixes. The fourth is not, and building it surfaced a hole the epic's own §5 risk table anticipated from the other side.

**The hole.** At or below `refusalRegardThreshold` (−3) a Hero refuses every Commission. Every way E2 gives a Hero to *gain* Regard runs through being sent out: a Vignette outcome during work. So a Hero who falls to −3 can no longer earn any of it back. The only remaining move is to insist, which costs two more and takes them to the Departure threshold. As drafted against a literal reading of E2-S3 — check only at or below `departureRegardThreshold`, and on success merely record that you talked them round — the bottom three points of the scale were a one-way ride to the door, and neglect that started by accident could not be repaired by anything the player did.

**Decision.**

1. **Backing's third term, as architecture §5 always said it would be.** `regardTerm = round(mean(member.regardForGuildmaster.value) / config.backingRegardDivisor)`, and the whole of `statTerm + traitTerm + regardTerm` is clamped to `[config.backingMin, config.backingMax]`. Two consequences of the clamp are worth stating because they change E1 behaviour: **Backing can now be negative**, so a Party of resentful Heroes is worse at the work; and `backingMax` is now the ceiling on the *whole* of it rather than on the Stat term alone, so a Guildmaster whose Stats already reach the ceiling gains nothing further from a Trait that carries `backing`. `backingMin` is −2 and `backingRegardDivisor` is 2, so the term runs −2..+2 over the −5..+5 Regard scale.
2. **Backing is computed after the insistence penalty, and `proposeParty` reports it before.** `proposeParty` answers the question "what would this Party be, as the world stands"; `commitParty` charges the refusing Heroes and *then* works the Backing out. So a Party committed over a refusal sets out with less Backing than the proposal described, and that gap is the visible price. Where nobody refuses the two numbers are identical, and a test asserts it.
3. **The Departure check is taken over a wider band than Departure itself.** At each Board refresh every Hero at or below `refusalRegardThreshold` is checked — `d20 + gm.Guile + gm trait modifiers` against `config.departureDc` (12). Passing it gains them `config.talkedRoundRegardGain` (**+3**, a new tunable) with the reason "you talked them round", which is enough to carry a Hero from the Departure threshold back above the refusing line so that they can be sent out and earn the rest themselves. Failing it loses them only if they are also at or below `departureRegardThreshold`; a Hero between the two lines who fails simply stays, and stays sullen. This is what makes Departure a relationship the player can still act on rather than a countdown.
4. **A Hero away on work is settled on the Day they come home.** Drift and the Departure check both skip a Hero out with a Party, and the check they were owed is taken on the return Day — after the `PartyReturned` that closes the Commission, so the work is always finished first. A Hero is never checked twice on the same Day. A Hero who comes home on a Day the Board is not refreshing is checked then even if no refresh fell while they were away, which is a small over-checking the contract is silent about. *(Corrected by later verification, recorded in [DL-15](#dl-15--e2-verification-two-backing-constants-named-pre-e2-saves-load-without-drift-and-the-e2-measurement): it is not true that such a Hero is on work only because the player insisted — a Hero committed at Regard −2 can be taken to −3 mid-Commission by a `heroRegardForGuildmaster` consequence (`collapsed-passage:failure`, `fever-in-the-wet:failure` and `quarrel-on-the-road:failure` each carry −1) and is then checked on return with nobody having insisted. The over-check is benign for a different reason: at −4/−3 the Check can only help — passing gains `talkedRoundRegardGain`, and failing loses nobody who is not also at or below `departureRegardThreshold` — so its real effect is that a Hero on a run of short Commissions may be checked more often than once per Board refresh, not that they are put at any extra risk of Departure.)*
5. **Drift is evaluated at the Board refresh, before the Departure check, and is not a new kind of fact.** A Hero for whom `day − max(lastCommittedOn, regardDecayedOn) ≥ regardDecayEveryDays × quartersFactor` loses `regardDecayAmount`, reported through `HeroRegardForGuildmasterChanged` with a distinguishing reason. `quartersFactor` reads `config.regardDecayQuartersFactor` when the Hall holds `quarters`, and the Hall cannot hold it until E3, so it is 1 throughout E2. Because drift runs first, a Hero it pushes under the Departure threshold is checked on the value it has just taken them to, in the same refresh.
6. **A save written by E1 loads without a format bump.** `formatVersion` stays 1. The ten `GameConfig` fields E2 adds, `Hero.lastCommittedOn`, `Hero.regardDecayedOn` and `ledger.departures` are filled from `defaultConfig`, from `joinedOn` and from zero respectively when a document does not carry them; every field E1 itself always wrote is still required, so a genuinely malformed save is still refused. Filling `lastCommittedOn` and `regardDecayedOn` from `joinedOn` means a Hero idle since before the rule existed is not handed a fistful of drift on the first refresh after loading. *(Corrected by [DL-15](#dl-15--e2-verification-two-backing-constants-named-pre-e2-saves-load-without-drift-and-the-e2-measurement): as built, `regardDecayedOn` was also filled from `joinedOn`, which has the opposite effect from the one intended here — a Hero idle since before E2 existed became instantly overdue and lost a Regard point at the very next Board refresh after loading. The fix fills `regardDecayedOn` from the Career's current Day instead, so drift is owed only from the Day the rule arrived. `lastCommittedOn` is still safely filled from `joinedOn`: the decay clock reads `max(lastCommittedOn, regardDecayedOn)` [§5 above], and `regardDecayedOn` — now the load Day — is never smaller than `joinedOn`, so it is always the one the `max` picks.)*
7. **Two authored Regard consequences were retuned.** `barred-gate`'s failure outcome loses its `heroRegardForGuildmaster` −1: it is the most-fired Vignette in the set and the grievance is a small one, and a point off a five-point scale every third time it fires took every Roster to the floor inside four years. `collapsed-passage` and `fever-in-the-wet` gain one on their failure outcomes, where the Guildmaster's judgement genuinely is at issue, and `terms-on-the-road` gains +1 on its critical. Regard moves where the decision was the Guildmaster's, and rarely.

**Consequences.** Backing changes shape once, here, as the risk table said it would, and the change is visible to a player as a Party that is worse at its work when it resents you. The new `talkedRoundRegardGain` is the one number in E2 that the epic did not name, and it is the one to turn if Departure comes to feel either inevitable or unreachable: at +3 a Hero at the Departure threshold who passes the Check lands at −2 and will take work again, and roughly two Checks in five are failed at DC 12 against a typical Guile.

Pinned by `engine/tests/refusal.test.ts`, `insistence.test.ts`, `departure.test.ts`, `decay.test.ts`, `backing.test.ts` and `gate.test.ts`, by the E1-save block in `engine/tests/save.test.ts`, and end to end by `engine/tests/gate.test.ts`, which plays seed `gate-3` to Retirement and loses a Hero who refused, was insisted upon, and walked out — Hero `h2`, Day 97 (E3's harm draws from the shared generator moved this from `h3` on Day 86; see DL-16 §2). `content/tests/balance.measure.test.ts` gains the E2 counters — departures, refusals by reason, work nobody would take, drift, final Roster Regard and mean committed Backing — so the next balance pass starts from numbers rather than from an argument; it is still skipped unless `HEROESIM_BALANCE` is set, and the E2 figures have not been measured at fleet scale. The 200-Career contract smoke in `engine/tests/api.test.ts` is unchanged and still passes, and its automatic policy deliberately never insists, so the Regard it measures moved only through work and neglect.

## DL-15 — E2 verification: two Backing constants named, pre-E2 saves load without drift, and the E2 measurement

**Status:** Accepted · **Date:** 2026-09-19 · **Decided by:** an agent, under the owner's standing instruction to build to the plan and to record what independent verification turns up · **Amends:** DL-14 §4 and §6, corrected in place above (not superseded) because DL-14 was itself written in this same uncommitted change and had not yet been accepted by the owner

**Context.** Independent verification of the built E2 found two defects and, for the first time, measured the epic's effect on a played Career.

1. **A literal balance number remained in Backing (F4).** `backingFor`'s Stat term, `Math.round((gm.Nerve + gm.Guile) / 2) − 2`, carried two literals CLAUDE.md invariant 8 forbids: `2` as the divisor and `2` as the offset. Both were inline since E1; E2 named the Regard term's own constants (`backingMin`, `backingRegardDivisor`) but had no occasion to touch this one, and E2's own definition of done said so honestly.
2. **Loading a pre-E2 save cost the Roster Regard on the spot (F1).** `fillFieldsAddedLater` filled a missing `Hero.regardDecayedOn` from `joinedOn`. Because the decay clock reads `day − max(lastCommittedOn, regardDecayedOn) ≥ regardDecayEveryDays × quartersFactor`, a save loaded long after its Heroes joined made every idle one instantly overdue, and the very next Board refresh cost each of them a Regard point — the opposite of the intent DL-14 §6 stated for the fill.
3. **The E2 figures were measured at fleet scale for the first time**, closing the gap DL-14's Consequences left open ("the E2 figures have not been measured at fleet scale"). Measured 2026-09-19 with `HEROESIM_BALANCE=1`, automatic policy, 300 seeds × 20 years, shipped defaults (DL-13's post-balance figure in brackets):

   retirement rate 94.0% (87.0%; target ≥ 80%) · final coin mean 57,692 / median 59,795 (29,720 / 30,430; target "low tens of thousands") · Beat mix failure 26.4% / success 44.8% / critical 28.8% (29.9 / 44.9 / 25.2; critical target 15–25%) · Patrons at or below floor 7.0% (14.2%) · empty Board refreshes 0.4% (0.6%) · Commissions per year 112.5 (95.5) · Commission success 68.5% (62.5%) · fees 6,281 against Upkeep 3,109 per year (5,100 / 3,168) · departures 0.16 per Career, 12.3% of Careers lost somebody · 2.0% of Heroes refusing at the end · drift 5.4 Regard lost per Career · mean Hero Regard at the end 1.00 · mean Backing committed 2.13 · the policy never insists. Failing-Guildmaster policy, 100 seeds: 100% insolvent, median Day 120 (unchanged from DL-13).

   **Two of these now sit outside DL-13's targets.** Final coin (mean 57,692 / median 59,795) is roughly double DL-13's post-balance figure and beyond "low tens of thousands"; the critical Beat share (28.8%) is above the 15–25% band DL-13 set, at the expense of failure (26.4%, DL-13 targeted 25–35%, still inside) and success (44.8%, still inside 40–50%). Stated as a hypothesis and not yet checked: Backing's new Regard term (DL-14 §1) lifts the mean committed Backing (2.13 here, against an E1 world with no Regard term at all), which adds to every Check's total and so plausibly lifts every Check, including into critical.

**Decision.**

1. **Name the two Backing literals.** `GameConfig` gains `backingStatDivisor` (2) and `backingStatOffset` (2), defaulted to preserve `backingFor`'s behaviour exactly. Both join `CONFIG_ADDED_LATER` in `save.ts` — the mechanism E2's ten fields already use — so a save from before they were named still loads and takes the defaults.
2. **Fill `regardDecayedOn` from the Career's current Day, not from `joinedOn`, on load.** `lastCommittedOn` keeps its `joinedOn` fill: the decay clock takes `max(lastCommittedOn, regardDecayedOn)`, and `regardDecayedOn` — now the load Day — is never smaller than `joinedOn`, so the `max` always picks it and `lastCommittedOn`'s own value never matters to this calculation. Drift is thereby owed only from the Day this rule arrived, which is what DL-14 §6 meant to say.
3. **The balance pass stays deferred, past E6 rather than started now.** Two measured figures sit outside DL-13's targets, but E3 (harm and a 700-coin Hall), E4 (joining fees and the larger Upkeep of a bigger Roster) and E5 (a soured Rival taking more of the Board) each move fee income, Upkeep or Backing again, and DL-13 itself already says E3's Hall and E4/E5's Transfers "add sinks rather than relief"; E6's turn-backs move the Beat mix and the fee actually collected once more on top. Tuning `talkedRoundRegardGain`, `departureDc` or `backingRegardDivisor` now would be tuning against a target that keeps moving under later epics; the pass happens once E3–E6 are built, against the game as it will actually ship, and starts from this measurement rather than from nothing.

**Consequences.** Backing's shape does not change again — DL-14 §1 still holds; only two of its constants gain names. A save from before this change still loads: `engine/tests/save.test.ts` gains a sibling block stripping `backingStatDivisor` and `backingStatOffset` and asserting they take their defaults, alongside the existing E2 block. A pre-E2 save goes on being played without an unearned Regard loss: the "a save written before E2 existed" block's "goes on being played" test now advances a pre-E2 document past the first Board refresh at or after `regardDecayEveryDays` Days from the load Day and asserts no drift fires before it and the first drift lands exactly there, rather than only asserting that nobody currently refuses. `talkedRoundRegardGain`, `departureDc` and `backingRegardDivisor` are named here as the dials for the deferred pass: the first two govern how easily a Hero returns from the edge of Departure and so how much of the Roster stays available to work (feeding Commissions-per-year and so fee income and final coin), and the third governs how far a resentful or a devoted Party's Backing moves off the mean implicated in the critical-Beat hypothesis above. `backingStatDivisor` and `backingStatOffset` are not listed as dials: they are named for CLAUDE.md invariant 8, not because independent verification found reason to move them.

## DL-16 — The E3 rules as built: ages derived from the seed rather than drawn from the Career, three named Hall costs, and Retirement taken before the Departure check

**Status:** Accepted · **Date:** 2026-09-19 · **Decided by:** an agent, under the owner's standing instruction to build E3 to the adopted defaults in [E3 §3](epics/E3-injuries-and-scars.md#3-known-unknowns--adopted-defaults) and to record only what the plan left open or what the build deviates from

**Context.** [E3](epics/E3-injuries-and-scars.md) §4 states most of the epic exactly — the config fields, the state, the events and the API — and §3 adopts its own defaults, so there is little left to decide. Building it against the contract turned up eight places where the plan is silent, or where following it literally would break something already built.

**Decision.**

1. **A Hero's starting age is derived from the Career's seed and their id, not drawn from the Career's shared generator.** `startingAge(seed, heroId, config)` seeds a throwaway xoshiro state from `"<seed>:age:<heroId>"` and draws one value in `[heroStartingAgeMin, heroStartingAgeMax]`. It is pure, it is the same number on every machine, and it consumes nothing from `career.rng`. Two things follow that a draw from the shared generator could not give. World generation is otherwise **bit-identical** to E2's: every Hero's name, Stats and Regard, every Patron, every Rival and the opening Board are what they were, so nothing that pins a generated world had to move for ages. And the definition of done's "Heroes without `age` are given one from the configured range" is satisfied by calling the *same* function at load: a pre-E3 save is filled with exactly the age world generation would have given that Hero, loading the same document twice gives the same ages, and `career.rng` is not advanced by the load — which drawing at load would have done, quietly putting a loaded Career on a different random path from an unloaded one.
2. **Harm does draw from the Career's shared generator**, because it is play rather than generation: a failed Check draws once for whether harm lands, and again for which Trait and how long it runs. This moves every seeded outcome after the first failed Beat. That was expected when the epic was written; the pinned values that moved are listed in the Consequences below.
3. **Hall costs are three named number fields, not the record E3 §4 sketches.** `hallInfirmaryCost` (200), `hallTrainingYardCost` (250) and `hallQuartersCost` (250) replace `hallImprovementCosts: { … }`. A nested table on `GameConfig` would break three mechanisms that are already built: `cloneCareer` copies the config with a spread, so a nested table would be *shared* between a Career and its copy; `deserialiseCareer` requires every field of `defaultConfig` to be a number and would refuse the save; and `--config key=value` (E2) can only set a number, so the costs would be the only tunables a test or a player could not try out. The three flat fields keep all three working and are exactly the numbers §3 adopted.
4. **`quartersRegardDecayFactor` is E2's `regardDecayQuartersFactor`, whose default moves from 1 to 2.** E3 §4 names a new field; E2 already built the read — `quartersFactor()` in `regard.ts`, DL-14 §5 — under a different name, and renaming it would break every save E2 wrote for no gain. The field keeps E2's name and E3 sells the improvement that switches it on, which is what DL-14 §5 said would happen. Nothing changes for a Guild whose Hall does not hold `quarters`.
5. **An Injury is a Trait carrying `liftsOn`**, as solution architecture §3 has said since E1. `availableHeroes` and `injuredHeroes` take no content and read `liftsOn` alone; `liftDueTraits`, which has the content in hand, reads the TraitDef's `kind`, so an Injury lifts as `InjuryLifted` and any other timed Trait as `TraitLifted`. The two tests agree for the whole of E3: every Trait the engine or the shipped content gives with a span is `kind = "injury"`. They would disagree the moment E6 gives a timed Trait that is **not** an Injury — E3 §4 reserves `TraitLifted` for exactly that — because such a Trait would make its holder unavailable for work. E6 closes that gap, by giving `availableHeroes` the content or by discriminating on the held Trait; it is recorded here rather than guessed at now.
6. **A Hero who dies leaves the Party as well as the Roster.** Their id is removed from `party.heroIds`, so later Beats of that Commission cannot draw them and `PartyReturned` names only who came back. A Party with nobody left comes home on the Day the last of them died rather than on `returnsOn`, with `succeeded: false` and no fee — the work is not finished by people who are not there, whatever the score had reached.
7. **Retirement is settled before Regard drift and before the Departure check.** All three run at a Board refresh, and on the return Day for a Hero who was away (E2's cadence, DL-14 §4). A Hero who has reached `heroRetirementAge` is therefore gone before the drift that would have soured them and before the Check that would have lost them: Retirement ends well, and a Hero old enough for it should not be made to walk out first. `HeroExit.reason` for Death and for Retirement are two more engine-owned reason constants, exactly as E2's Regard reasons are.
8. **`PartyProposal.unavailable` lists the whole Roster's unavailable members, not only the Heroes the proposal names.** A front end greys out the names it is *not* going to be allowed to send, so the list has to cover everybody; naming a Hero who is away or injured still throws `HeroNotAvailable` from both `proposeParty` and `commitParty`, as E2's shared `requireParty` always did. Where a Hero is both away and injured the reason reported is `'away'`, because that is the fact that stops them being picked today.

**Consequences.** The Scar the engine draws is any `kind = "scar"` Trait in content, which includes the two refusing Scars E2 shipped: `content/traits.toml`'s own comment said so when they were written — "nothing in E2 hands it out: a Hero becomes Worn, and E3 is where a Scar like it is given". A Hero who takes `Worn` refuses every Commission afterwards and will drift out of the Guild unless the Guildmaster talks them round, which is a career ending badly rather than a defect.

`TraitGained` still fires for every Injury and Scar, before the `HeroInjured` or `HeroScarred` that narrates it. `narrate` makes a pre-pass over the events of a call and stays silent on a `TraitGained` that a `HeroInjured` or `HeroScarred` on the same Day, Hero and Trait already tells, so nothing is said twice; a Trait given by anything else still gets its own note.

Pinned seed-specific values moved in exactly one file, and only because harm now draws from the shared generator (§2). `engine/tests/gate.test.ts` plays seed `gate-3` and pinned the departing Hero as `h3` on Day 86; the arc still happens on the same seed under the same policy and now falls on a different Hero and Day, which the test re-pins with a note saying so. The same file's `heroesLost === formerHeroes.length` no longer holds, because E3-S3 makes the reckoning count Death and Departure and report Retirement apart from them; it now compares against the former Heroes whose exit is not a Retirement. Nothing else in E1's or E2's suites needed a line changed — E1's Check rule is untouched — beyond the three additions every new `EngineErrorCode` and event member forces by design: the exhaustive maps in `engine/tests/events.test.ts` and `narrate/tests/errors.test.ts`.

**One acceptance box of E3-S3 is not met and cannot be at these defaults**, and it is ticked `[ ]` in the epic with the measurement beside it: "`formerHeroes` after a full Career contains a mix of all three exit kinds on most seeds". Deaths run at 0.12–0.48 per Career and Departures at 0.01–0.11, so the joint chance of all three kinds inside one Career is under one per cent — 0 of 200 fixture Careers and 0 of 300 authored ones. All three kinds are reachable — the smoke run requires a Death and a Retirement across the fleet and E2 proves Departure deterministically — what is not true is "on most seeds", and making it true needs a death rate §3 deliberately set well under one per cent of Beats. It is left for the deferred balance pass rather than tuned here.

The balance pass stays deferred past E6 ([DL-15](#dl-15--e2-verification-two-backing-constants-named-pre-e2-saves-load-without-drift-and-the-e2-measurement) §3). `content/tests/balance.measure.test.ts` gains the E3 counters — Injuries, Scars, deaths, retirements and Hall purchases per Career — so the pass starts from numbers rather than from an argument. The automatic policy there now buys a Hall improvement when it can comfortably afford one, and it never commits an injured Hero, which `availableHeroes` enforces for it rather than the policy remembering to.

Measured 2026-09-19 with `HEROESIM_BALANCE=1`, automatic policy, 300 seeds × 20 years, shipped defaults (DL-15's E2 figure in brackets):

retirement rate 78.7% (94.0%; target ≥ 80%) · final coin mean 35,690 / median 37,885 (57,692 / 59,795; target "low tens of thousands") · Beat mix failure 24.8% / success 44.9% / critical 30.4% (26.4 / 44.8 / 28.8; critical target 15–25%) · Patrons at or below floor 6.0% (7.0%) · empty Board refreshes 0.0% (0.4%) · Commissions per year 83.3 (112.5) · Commission success 71.4% (68.5%) · fees 5,045 against Upkeep 2,846 per year (6,281 / 3,109) · mean Backing committed 2.71 (2.13) · **harm: 292.9 Injuries, 4.64 Scars, 0.48 deaths and 0.83 Retirements per Career; 37.7% of Careers lost somebody to a Death and 54.7% retired somebody** · Hall: 2.70 improvements bought per Career, 89.3% bought all three, the first on a median of Day 28 · drift 52.3 Regard lost per Career (5.4) · mean Hero Regard at the end −0.19 (1.00) · departures 0.01 per Career (0.16). Failing-Guildmaster policy, 100 seeds: 99% insolvent, median Day 130 (100%, Day 120).

**Three of these are worth naming for the deferred pass.** Commissions per year falls from 112.5 to 83.3 and the retirement rate with it, from 94.0% to 78.7% — just under DL-13's floor of 80% — because an injured Hero cannot be sent and a four-Hero Roster spends a real share of twenty years short-handed; `injuryChanceOnFailure` is the dial nearest to that, and E4's Applicants will move it from the other side. Final coin falls from 57,692 to 35,690, which brings it back inside DL-13's "low tens of thousands" for the first time since E1's pass — the Hall is a 700-coin sink and fewer Commissions are taken. And drift rises tenfold, from 5.4 to 52.3 Regard lost per Career, because an injured Hero is an idle Hero and idleness is exactly what drift charges for; the Roster ends a Career at a mean Regard of −0.19 rather than +1.00. Departures did not rise with it, because the quarters the policy buys on 89% of Careers double the idle threshold and the Departure Check talks most of them round.

## DL-17 — E3 verification: what harm costs at the adopted defaults, and four questions left for the balance pass

**Status:** Accepted · **Date:** 2026-09-19 · **Decided by:** an agent, under the owner's standing instruction to build to the plan and to record what independent verification turns up. §1 is a decision taken in this same change, under CLAUDE.md invariant 8. **§§2–5 are open questions for the owner, each carrying a recommendation rather than a decision taken; nothing in them has been built or changed.** §6 is an observation, not a decision.

**Context.** E3's own risk table ([E3 §5](epics/E3-injuries-and-scars.md#5-risks-and-mitigations)) expected harm's spiral to run through failed Commissions. Independent verification played E3 out at fleet scale, at the epic's own adopted defaults, across several Hall-buying policies, and found a different and harsher shape than the table anticipated — a measured fact this entry puts on record before E4 is measured against it, together with four questions the measurement raises that only the owner can settle.

**Decision.**

1. **The Patron Regard recovery amount is a named `GameConfig` field (Fix 3, invariant 8).** `recoverPatronRegard` in `career.ts` called `changePatronRegard(draft, patron, 1, …)`, carrying a literal `1` for how far a negative Patron Regard recovers towards zero every `patronRegardRecoveryEveryDays`. `GameConfig` gains `patronRegardRecoveryAmount` (default 1, documented beside `patronRegardRecoveryEveryDays`), preserving `recoverPatronRegard`'s behaviour exactly at the default. It joins `CONFIG_ADDED_LATER` in `save.ts`, the mechanism DL-15's two Backing constants already use, so a save from before it was named still loads and takes the default. Pinned by a new case in `engine/tests/loop.test.ts` that sets it to 2 and asserts the recovery lands at 2 rather than 1.

2. **E3 at the adopted defaults is materially harsher than the epic's risk table anticipated — a measured fact, to be read before E4 is measured.** Verifier's figures, 120 seeds, share of Careers reaching Retirement, fixture content / authored content: E2 as it was 100.0% / 88.3%; E3 with no Hall bought 50.0% / 20.8%; infirmary only 75.0% / 32.5%; training yard only 80.8% / not measured; quarters only 70.0% / not measured; all three 90.8% / 63.3%. Separately, 200 fixture seeds: 91.5% with the Hall-buying policy, 49.5% without. The builder's own balance harness (300 authored seeds, its own policy) measured 78.7% (DL-16, above); the two policies differ, so **these figures are not comparable and must not be quoted side by side.** Share of Roster Hero-Days spent injured: 34.6% on authored content with no Hall, 19.5% with all three. The spiral runs through Upkeep on a Roster that cannot work, not through failed Commissions as the risk table expected. The test policies in `engine/tests/fixtures.ts` and `content/tests/parse.test.ts` buy Hall improvements; without that, `api.test.ts`'s untouched `retirement >= 0.6` assertion fails at about 50% — so **no un-helped baseline is asserted anywhere in the suite.** E4's Applicants are the designed relief for this: E4 must be measured against E3-without-Applicants, not against E2, or Applicants will be credited with undoing difficulty E3 itself introduced.

3. **Open question for the owner: should an injured Hero drift?** E2 says a Hero away on a Commission does not decay and is silent on an injured one. As built, an injured Hero does drift, so harm became a Regard cost as well as a work cost: drift rose from 5.4 to 52.3 Regard lost per Career (builder's harness, DL-16 above) and mean end-of-Career Roster Regard fell from about +1.0 to about −0.2 (−0.51 with no Hall). Against drifting them: drift models neglect, and a Guildmaster who cannot send an injured Hero out is not neglecting them. For it: a Hero left alone in the Hall for a month may fairly resent it regardless of why. **Recommendation:** pause drift while a Hero is injured, behind a named `GameConfig` switch, decided in the deferred balance pass (DL-15 §3). Not changed here.

4. **Open question for the owner: `Worn` in the Scar pool.** `Worn` is one of six authored Scars and an unconditional refusal (`refusal: {}`); it lands on about 0.8 Heroes per Career. Left alone, such a Hero costs Upkeep for roughly 290–350 Days (570–690 with quarters bought, which double the idle threshold) before drift and a failed Departure Check take them, and the Check is passed about 60% of the time, each pass lifting them `talkedRoundRegardGain` (+3) while they carry on refusing. Two things make this an arc rather than a trap: the player can act, by insisting — each insistence sends them out at Might −1 / Nerve −1, costs `insistenceRegardCost`, and brings the Departure Check nearer — and from E4 a Roster place taken by a Hero who will not work is an opportunity cost rather than paralysis. **Recommendation:** leave `Worn` in the pool; if it reads as too punishing in play, moving it out is a content edit, not an engine change. Not changed here.

5. **Open question for the owner: the unmet acceptance box's criterion.** "`formerHeroes` after a full Career contains a mix of all three exit kinds on most seeds" ([E3-S3](epics/E3-injuries-and-scars.md#e3-s3-age-retirement-and-the-exit-ledger), unticked) is unreachable at the adopted defaults under any policy measured, and the binding constraint is Departure, not Death: under the Hall-buying policy, P(≥1 Death) 9.2%, P(≥1 Departure) 0.8%, P(≥1 Retirement) 70.0%, joint about 0.05%; with no Hall, 26.7% / 13.3% / 39.2%, joint about 1.4% (2 of 120 observed). Departure is rare because the policy measured never insists and buys quarters, not because the death rate is too low, which corrects the reading DL-16 gave this box. **Recommendation:** the balance pass should look at the criterion itself, since it also shows E2's headline mechanic is nearly switched off under a sensible Hall-buying policy. Not changed here.

6. **`ledger.heroesInjured` counts Injuries, not Heroes**, about 240 per Career. Self-consistent with its own tests, and named honestly in the field's own sense, but the field's *name* says Heroes. No front end shows it yet. Left as it is; E7 must decide what the reckoning says before it prints it.

**Consequences.** DL-16's reading of the unmet acceptance box, above, named the cause as §3's death rate; §5 above corrects that: the binding constraint is Departure, and the epic file's own annotation on that box now cites this entry. Nothing else DL-14, DL-15 or DL-16 decided is disturbed — §2–5 above are questions and recommendations for the deferred balance pass (DL-15 §3), not decisions, and the game behaves exactly as DL-16 left it except for §1's named field.

**E4 must know**, from the same verification pass: ages are derived from `"<seed>:age:<id>"` (DL-16 §1), so an Applicant's id must stay uniquely namespaced against every Hero that has ever existed in the Career, and a *returning* former Hero must have `age` set explicitly from the record they left with, never re-derived from the id — re-deriving would hand them the age they would have started at, not the age they actually are. `calibreStatBudget`, or whatever E4 names the field gating an Applicant's calibre, should be flattened to three named fields rather than one table, for the same three reasons DL-16 §3 gave the Hall's costs: `cloneCareer` copies `GameConfig` with a spread, so a nested table would be shared rather than copied; `deserialiseCareer` requires every `GameConfig` field to be a number; and `--config key=value` can only set a number. And harm draws from the Career's shared generator (DL-16 §2), so any new draw `newCareer` or the Day loop takes moves every seeded pin after it — prefer a derived stream, in the way `startingAge` is derived rather than drawn, for a property that belongs to one thing rather than to the sequence of play, and where a new draw from the shared generator is unavoidable, add it at the end of a sequence rather than in the middle of one.

## DL-18 — Four read-only selectors the front ends were restating are exported from the engine

**Status:** Accepted · **Date:** 2026-09-19 · **Decided by:** an agent, under the owner's standing instruction to build to the plan. The rule applied is not invented here: [E7 §4](epics/E7-terminal-ui-and-saves.md#4-technical-notes) already says "if a view wants something not on this list, the selector is added to the epic that owns the data, with its own unit tests… It is never computed in `cli/`", and [E8-S2](epics/E8-web-front-end.md#e8-s2--state-and-one-place-decisions-are-made--1-day) already says "nothing in `web/` computes a rule". This entry is that rule being followed, not a new one being set.

**Context.** With E2 and E3 built, both front ends had quietly started restating engine facts the engine itself does not export, in four places:

1. **Who cannot be sent, and why.** `engine/src/refusal.ts` has `unavailableAmong(career)`, answering exactly "away beats injured" for the whole Roster, but `engine/src/index.ts` did not re-export it. `web/src/state/selectors.ts` carried a private fallback, `unavailableWithoutAParty`, restating the same precedence for the one case `proposeParty` will not take a Commission through, and `web/src/panes/Roster.tsx`'s `whereLine` decided the same away-versus-injured ordering a third time, for itself, by checking which of `partyOf` and `injuredUntil` returned a value first.
2. **Upkeep due.** `web/src/state/selectors.ts`'s `upkeepDue` was `upkeepBase + upkeepPerHero × roster.length` — the same expression `payUpkeep` in `engine/src/career.ts` already computed — and `cli/src/display.ts`'s `statusLines` held a third copy of it inline.
3. **Countdowns.** `web` had a private `daysUntilMultiple`, restating the Day loop's own private schedule test (`fallsDue(day, every)` in `career.ts`) as "Days until next", for both the Upkeep and the Board-refresh clocks; the CLI had its own `nextDayOn` doing the equivalent arithmetic the other way round (the next absolute Day, rather than the interval to it). Both fed "Next Upkeep … in N Days" and "Board refreshes in N Days", and neither could be proved to agree with the Day the engine's own loop actually settles either event on, because neither read the loop's schedule test at all.
4. **The Year a Day falls in.** `web/src/state/storage.ts`'s `yearOf` restated `Math.floor((day − 1) / daysPerYear) + 1`, which `narrate`'s `formatDay` and `engine/src/state.ts`'s `buildReckoning` (`years: Math.floor((career.day − 1) / config.daysPerYear)`) each also carried, independently, as three copies of the same arithmetic.

None of this is a defect in E2 or E3 — both epics shipped a correct, complete engine surface for what they were asked to expose — it is E7 §4's list not yet having grown to cover what E7 and E8 actually needed, because E7 itself has not been built yet. E7 §4 states plainly that "E7 adds no state, no config field, no event and no engine function", which is a promise E7 can only keep if the data it needs is already sitting in the engine by the time it is built.

**Decision.** Add four selectors to the engine, each attributed to the epic that owns the data it reads — E1 owns the Career's shape, its Upkeep and its Days and Years; E3 owns who is away or injured — precisely so that E7, when it is built, adds none of its own and keeps its own promise:

1. **`unavailableAmong(career)` (E3)** — already written in `engine/src/refusal.ts` for E3-S2, now re-exported from `engine/src/index.ts`. No behaviour change.
2. **`upkeepDue(career): number` (E1)**, in `engine/src/career.ts`, beside `standing`/`availableHeroes`/`injuredHeroes`. `payUpkeep` now calls it, so there is one expression for "what Upkeep costs", not two.
3. **`daysUntilUpkeep(career): number` and `daysUntilBoardRefresh(career): number` (E1)**, in `engine/src/career.ts`, built on the Day loop's own `fallsDue(day, every)` — the private schedule test `stepDay` itself uses — rather than a second copy of its arithmetic, so a countdown cannot disagree with the Day the thing it counts down to actually happens on. Definition, on the Day it falls due: `stepDay` settles that Day's Upkeep or Board refresh *before* any caller ever sees the resulting Career, so on a Day that is itself due the countdown reports the interval to the **following** one rather than zero — which is what both front ends were already showing, and is why "never zero" was already true of the code being replaced.
4. **`yearOf(day, config): number` and `dayOfYear(day, config): number` (E1)**, in `engine/src/state.ts` beside `retirementDay`/`nextRefreshDay`. `buildReckoning`'s `years` field now reads `yearOf(career.day, config) − 1`, and `narrate`'s `formatDay` — which already imports from `@heroesim/engine` — now calls both, so there is one definition of a Year rather than three.

The duplicates are removed at the same time: `web/src/state/selectors.ts` deletes `unavailableWithoutAParty` and `daysUntilMultiple`, and its `upkeepDue`, `daysUntilUpkeep` and `daysUntilRefresh` become thin pass-throughs to the engine; `web/src/state/storage.ts`'s `yearOf` becomes a thin pass-through; `web/src/panes/Roster.tsx`'s `whereLine` takes its away-or-injured reason from `unavailableAmong`, asked once per Roster render, instead of deciding the ordering itself; `cli/src/display.ts`'s `statusLines` calls the engine's `upkeepDue`, `daysUntilUpkeep` and `daysUntilBoardRefresh` in place of its own inline expression and its calls to `nextDayOn`.

**Consequences.** No displayed value changes: `cli/tests/display.test.ts`, all of `web/tests/` and all 51 Playwright checks (17 per project) pass exactly as they stood, with one exception, which is a strengthening rather than a behaviour change — `web/tests/selectors.test.ts`'s "still answers when the engine will not take a Party at all" now also asserts the no-Party, nobody-free case against `unavailableAmong` imported directly from `@heroesim/engine`, rather than only against a hand-written expectation, because the private fallback it used to exercise no longer exists to be exercised. `engine/tests/selectors.test.ts` is new: it proves `upkeepDue` against the magnitude of the `CoinChanged` (reason `'upkeep'`) the engine actually pays, for Rosters of 0, 1 and 4 Heroes; it walks a Career a full cycle at a time for at least 45 Days at both the default and a non-default interval, for both countdowns, asserting the promised event lands on exactly the promised Day and never before; it checks `yearOf`/`dayOfYear` at Day 1, the last Day of Year 1, the first Day of Year 2 and Day 7201, at the default `daysPerYear` and a non-default one, and that the reckoning's own `years` agrees; and it deep-freezes a Career to prove all four are read-only.

`cli/src/display.ts`'s `nextDayOn` is kept, unused by `statusLines` now, rather than deleted: `cli/tests/display.test.ts` pins it directly as a standalone day-math primitive (`nextDayOn(1, 10)` and so on), independent of any Upkeep- or Board-shaped meaning, and this change touches no test file but `web/tests/selectors.test.ts` above. Only its former role — feeding it `career.config.upkeepEveryDays` and `boardRefreshEveryDays` to reconstruct a schedule the engine already knows — is gone; the function itself is left for the owner to remove later if nothing else wants it.

**Not in scope, and known:** the two front ends' difficulty-band labels ('Gentle/Testing/Grim' in `web`, 'easy/fair/hard/grim' in the CLI) still differ. That is presentation wording, not a restated rule — both bands are computed independently from `career.config.difficultyMin`/`difficultyMax`, correctly, and neither restates the other's words — and is left for E7 or E8-S6 to settle, not this entry.

DL-01 through DL-13 are accepted and untouched by this entry.

## DL-19 — The E4 rules as built: Applicants drawn from a stream of their own, ids that never repeat, a flat calibre budget, and a returner who keeps their id and brings their age forward

**Status:** Accepted · **Date:** 2026-09-19 · **Decided by:** an agent, under the owner's standing instruction to build E4 to the adopted defaults in [E4 §3](epics/E4-recruitment.md#3-known-unknowns--adopted-defaults) and to record only what the plan left open or what the build deviates from

**Context.** [E4](epics/E4-recruitment.md) §4 states most of the epic exactly — the config fields, the state, the events and the API — and §3 adopts its own defaults. Building it against the contract, and against E2 and E3 as they were actually built, turned up eleven places where the plan is silent, or where following it literally would break something already standing. [DL-17](#dl-17--e3-verification-what-harm-costs-at-the-adopted-defaults-and-four-questions-left-for-the-balance-pass)'s "E4 must know" paragraph named three of them in advance; this entry settles those and the rest.

**Decision.**

1. **Applicant generation draws from a stream derived from the Career's seed and the Day, never from `career.rng`.** `applicantStream(seed, day)` seeds a throwaway xoshiro state from `"<seed>:applicants:<day>"`, exactly as `startingAge` seeds one from `"<seed>:age:<id>"` (DL-16 §1), and every draw a batch takes — how many arrive, which former Hero comes back, each calibre, each name, each Background, each set of Stats — comes from it. Four things follow, and they are the whole reason for it. No existing seeded expectation moved: the Day loop takes not one extra draw from the shared generator, so every Beat, every Board and every Check in E1's, E2's and E3's suites is bit-identical to what it was. E4-S2's "batch arrival is deterministic from the seed" is trivially true rather than argued. A batch arriving on the same Day a Commission resolves cannot shift that Commission's Beats. And declining or ignoring an Applicant cannot change how anything else in the world unfolds, which is what makes "recruitment is entirely optional" a fact about the simulation rather than a hope. DL-17 asked for exactly this ("prefer a derived stream … for a property that belongs to one thing rather than to the sequence of play").

2. **An Applicant's id is `a<n>`, from a monotonic counter on the Career; a returning former Hero keeps the id they left with.** `Career.nextApplicantNumber` starts at 1, is serialised with the Career and only ever goes up, so a fresh Applicant's id is never reused inside a Career even after they expire, and `a<n>` can never collide with a Roster Hero's `h<n>`, a Patron's `pa<n>`, a Rival's `r<n>`, a Commission's `c<day>.<n>` or a Party's `p<day>.<n>`. **`a` is reserved for Applicants: E5 must namespace a Rival's Heroes somewhere else**, because ages are derived from `"<seed>:age:<id>"` and two people sharing an id would share an age. An accepted Applicant becomes a Hero with the same id, as E4-S3 requires. A **returner** is the one exception to the counter: they come back under their own former id, so their history, the `regardFor` entries other Heroes still hold for them and the name the player remembers all stay attached to one person. Their id is therefore in `formerHeroes` and in `applicants` at once while the offer stands, and in exactly those two; accepting moves them to the Roster and out of `formerHeroes`, declining or expiring leaves them in `formerHeroes` to be offered again later. The generator is defensive as well as monotonic: an id already in use anywhere in the Career is skipped, so a save whose counter has been tampered with still cannot produce two people with one id.

3. **`calibreStatBudget` is three flat number fields, not the table E4 §4 sketches.** `calibreStatBudget1` (10), `calibreStatBudget2` (12) and `calibreStatBudget3` (14) replace `calibreStatBudget: { 1: 10; 2: 12; 3: 14 }`, for the three reasons DL-16 §3 gave the Hall's costs and DL-17 restated for this field, each of which was checked against the code again here: `cloneCareer` copies the config with a spread, so a nested table would be *shared by reference* between a Career and its copy; `deserialiseCareer` requires every field of `defaultConfig` to be a number and would refuse the save; and the CLI's `--config key=value` can only set a number, so the budgets would be the only tunables a test or a player could not try out. The numbers are exactly the ones §3 adopted.

4. **Recruitment is settled at the start of the Day — expiry first, then arrival — and `ApplicantsArrived` joins the attention set.** Both sit immediately after Injuries lift and the Roster ages, before any Beat. Expiry before arrival means that on a Day which is both (`applicantLingerDays` and `applicantsEveryDays` are both 20, so every arrival Day after the first is also an expiry Day) the player is never shown a fresh batch and a stale one together. An Applicant's `expiresOn` is `arrivedOn + applicantLingerDays` and they are gone at the start of that Day, which is the same reading `commitParty` already takes of a Commission's `expiresOn`. Because `advance` and `advanceUntilAttention` never step a Day of an ended Career, nothing can arrive once the Career has ended without a special case. `advanceUntilAttention` stops on `ApplicantsArrived`: people turning up is exactly the kind of thing a stretch of Days exists to stop for. At the shipped defaults this changes no behaviour at all, because 20 and 10 are both multiples of `boardRefreshEveryDays`, so every arrival Day was already a Board-refresh Day and already a stop.

5. **Accepting: the order of the three events, the Regard seeded both ways, and one more named constant.** `acceptApplicant` emits `ApplicantAccepted`, then `CoinChanged` with `reason: 'recruitment'`, then `HeroJoined`, which is the order [E5-S2](epics/E5-rivals.md) already fixes for its own Transfer (`HeroTransferred`, then `CoinChanged`, then `HeroJoined`) — the transaction, what it cost, and then the fact about the Roster. `regardFor` is seeded in both directions in the same step: the newcomer gains one for every Hero already on the Roster and every one of them gains one for the newcomer, and the Guildmaster's own `regardFor` gains an entry too, so no map is left with a hole in it. The value is a new `GameConfig` field, `joiningRegardAmongHeroes` (0), rather than the literal zero "neutral" would otherwise put in rules code, because CLAUDE.md invariant 8 makes a balance literal in rules code a defect and how warmly a Roster receives a stranger is a balance number. A **returner keeps every `regardFor` entry they left with** and is only given new ones for people who arrived after they went: somebody coming back remembers who they worked with, and inventing a fresh neutral opinion would throw that away.

6. **A returner brings their Traits, their Scars and their age forward; an Injury that healed while they were away is gone.** `age` is set **explicitly** to the age they left with plus the whole years elapsed, `floor((day − exit.onDay) / daysPerYear)`, and is never re-derived from `startingAge` — re-deriving would hand them the age they would have *started* at rather than the age they are (DL-17). Every Trait comes with them except one whose `liftsOn` has already passed, which is dropped: they were not going to spend a year at home with a broken rib, and E4-S4's "an unexpired Injury keeps its original `liftsOn`, so they may join injured" only makes sense if an expired one does not. A returner may therefore carry `Worn` and refuse everything from the moment they join, which is a Roster place spent badly rather than a defect (DL-17 §4), and a returner may be old enough to retire at the next Board refresh, which is a career ending as it should.

7. **A returner's calibre is what their Stats already earn, clamped to `maxCalibre(career)`; nothing gives a Hero a `calibre` field.** Calibre on an Applicant does two things: it sets the Stat budget a fresh one is generated against, and it sets the asking fee. A returner's Stats are not regenerated, so their calibre is read back off their Stat total — the highest budget that total reaches — and then clamped by Standing like anybody else's, so CONTEXT.md's "Standing … has exactly one job: gating the calibre of Applicants" holds for **every** Applicant without an exception to remember. `HeroJoined.calibre` is the accepted Applicant's calibre, read at the moment of acceptance; `Hero` gains no `calibre` field in E4, because nothing in E4 needs one and [E5 §4](epics/E5-rivals.md) is where it lands ("E4 introduced it on Applicant; E5 carries it onto Hero"). That is the minimum honest way to fill the event the epic specifies without building E5's state early.

8. **Eight read-only exports, not four: four front-end selectors and four pure helpers, none of them restated in a front end** (the rule DL-18 followed, and [E7 §4](epics/E7-terminal-ui-and-saves.md#4-technical-notes) states). Corrected in place by independent verification (DL-20 §Fix 3): the four selectors were named here, but `engine/src/index.ts` also exports four pure calibre-and-fee helpers that this section left out, and architecture §6 accordingly documented the selectors and not the helpers. **The four front-end selectors** — `maxCalibre(career)` and `applicantById(career, id)`, which E4 §4 already names; `acceptRefusal(career, applicantId)`, which answers "can this Applicant be taken on, and if not why" with the very `EngineErrorCode` `acceptApplicant` would throw plus the coin shortfall, so both front ends can write the reason out in words without either of them deciding what "full" or "cannot afford" means; and `applicantOffers(career)`, which is that answer plus the Days left before each Applicant gives up, for every live Applicant at once. E7 §4's dependency list grows by all four. **The four pure helpers**, each already used inside `applicant.ts` and exported so a front end or a later epic never has to restate them: `applicantInterval(career)`, how often a batch is due as the Roster stands; `calibreStatBudget(calibre, config)`, the Stat total a fresh Applicant of a calibre is generated against; `applicantFee(calibre, config)`, what an Applicant of a calibre asks for; and `calibreOfStats(total, config)`, the calibre a Stat total already earns, which a returner's fee is priced from (§7 above). E5 needs `calibreOfStats` and `applicantFee` to carry calibre onto `Hero` and to price a Transfer, which is why they were exported here even though nothing in E4 itself calls them from outside `applicant.ts`.

9. **Saves: `applicants` takes `[]`, and the id counter is derived from the ids the document actually carries.** `formatVersion` stays 1. The nineteen `GameConfig` fields E4 adds join `CONFIG_ADDED_LATER`, `ledger.applicantsSeen`/`applicantsAccepted`/`returners` and `ended.reckoning.heroesRecruited` fill from zero, and `Hero.formerHeroId` is optional and simply absent on everybody who was never away. `nextApplicantNumber` is **not** filled from zero: it is filled from one past the highest `a<n>` any Applicant in the document carries, so that a save written by hand, or by a front end, or by a version of this engine that had lost count, can still never mint an id somebody is already using. Applying DL-15's care to the first Day after a load: an E3 save loads with an empty batch, and the very next arrival Day behaves exactly as it would have in an unbroken Career, because arrival depends on the Day, the Roster size and Standing and on nothing a load has to invent.

10. **The two automatic test policies do not accept Applicants, deliberately.** `engine/tests/fixtures.ts`'s `autoPlay` and `content/tests/parse.test.ts`'s copy of it are left exactly as they were. Two things follow. Every rate and every pinned value in `api.test.ts`, `gate.test.ts`, `e3-gate.test.ts` and `parse.test.ts` still measures the same world it measured before, so nothing there had to be re-pinned or loosened. And the un-helped baseline DL-17 §2 said was missing everywhere in the suite — E3 with no Applicants — stays measurable, which is the only way E4 can be measured against E3 rather than against E2. E4's own gate, its 200-seed smoke and the balance harness bring their own accepting policies.

11. **The "no Commission, fee or Board decision reads `standing`" guard test lives in `content/tests/`.** ESLint forbids `node:*`, `fs` and `path` under `engine/**/*.ts`, which covers `engine/tests` as well as `engine/src`, so the one test in E4 that has to read the engine's own source cannot live beside the code it guards. `content/tests/` is a Node-environment Vitest project that already reads the repository's files, and `web/tests/engine-imports.test.ts` is the precedent for a static source scan living in whichever test project is allowed to open one. It is `content/tests/e4-standing-callsites.test.ts`; it lists every call site of `standing`/`standingOf` in `engine/src` as a file-to-count map, and it names `board.ts`, `beat.ts`, `check.ts`, `harm.ts`, `hall.ts`, `refusal.ts` and `regard.ts` as files that must hold none at all.

**Consequences.** Nothing E1, E2 or E3 pinned moved. No assertion was loosened, and the only edits to existing test files beyond two drivers named below are the two exhaustive maps that every new event member and every new `EngineErrorCode` forces by design — `engine/tests/events.test.ts`'s `EVERY_EVENT` (25 members to 29) and `narrate/tests/errors.test.ts`'s `CODES` (8 codes to 10) — plus the E4 counters added to `content/tests/balance.measure.test.ts`, which is a measurement rather than an assertion. Corrected by independent verification (DL-20 §Fix 3): two existing drivers **were** changed, both necessarily and both commented in place. `engine/tests/decay.test.ts`'s `DRIFT_ALONE` (~line 25) and `engine/tests/loop.test.ts`'s "stops at the Career's end" case (~line 673) each add `applicantsEveryDays: 0, applicantsEveryDaysBelowFloor: 0`, switching Applicants off for the same reason each file already puts its own subject out of reach of everything else: `decay.test.ts` measures drift alone, and an arriving batch is another rule moving the count in the middle of it; `loop.test.ts` sets `boardRefreshEveryDays: 1000` to prove `advanceUntilAttention` stops at the Career's *end* and nothing earlier, and — because `ApplicantsArrived` joined the attention set (§4 above) — a starting Roster of four sitting below `rosterFloor` would otherwise bring a batch on Day 10 and stop the stretch there instead. Both edits switch a rule off rather than change what either file asserts; no assertion was weakened by either one.

A Roster place is now an opportunity cost, which is what DL-17 §4 said would turn `Worn` from a trap into an arc: a Hero who refuses everything costs Upkeep *and* the place somebody else could have taken. The cap of twelve is hard, and `acceptApplicant` refuses at it rather than pushing somebody out — the design gives the player no firing mechanic, and that asymmetry is the point (E4 §0).

**§12 — what Applicants are worth, measured against E3 without them.** [DL-17](#dl-17--e3-verification-what-harm-costs-at-the-adopted-defaults-and-four-questions-left-for-the-balance-pass) §2 requires E4 to be measured against E3-without-Applicants rather than against E2, and noted that no un-helped baseline was asserted anywhere in the suite. `content/tests/balance.measure.test.ts` now runs four arms over the same seeds — with and without an accepting policy, crossed with and without Hall-buying — and the first of them is that baseline. The recruiting arms take on whoever the engine will let them while short-handed, and keep a full `startingCoin` of runway back once the Roster reaches the floor.

**Three things this says, and one of them was not expected.** Applicants are exactly the relief DL-17 §2 described for a Guild that has *not* bought the Hall: 32.5% of Careers reach Retirement with neither, 48.3% with Applicants alone. The Guild is also unmistakably healthier by every measure that is not survival — Commissions per year nearly trebles, the share that succeed rises, almost no Patron falls silent, and the Roster ends a Career thinking well of the Guildmaster (+1.46 against −0.13) rather than badly of it, because twelve Heroes means nobody sits idle long enough to drift.

**But a Guild that has bought the Hall is measurably *worse* off for recruiting to the cap: 80.0% reaching Retirement falls to 60.0%.** The cause is plain in the table and is not subtle: Upkeep is `upkeepBase + upkeepPerHero × roster.length`, so a Roster of twelve owes 248 coin every ten Days against 88 for four, and yearly Upkeep goes from 2,849 to 8,857 while fee income only doubles. The economy E4 §5's risk table priced — "a full Roster costs 146 coin per cycle against a 50-coin baseline" — was priced against DL-06's Upkeep, which [DL-13](#dl-13--the-e1-balance-pass-commission-score-counted-once-a-wider-critical-margin-patron-regard-that-recovers-and-an-economy-where-coin-is-tight) §5 then raised from 12+2 to 20+8 per Hero without E4 existing yet to be re-priced against. A full Roster is now 248 a cycle against an 88 baseline, not 146 against 50.

**Nothing is rebalanced here.** [DL-15](#dl-15--e2-verification-two-backing-constants-named-pre-e2-saves-load-without-drift-and-the-e2-measurement) §3 defers the balance pass past E6, and E5's Transfers and E6's turn-backs move fee income and Upkeep again; tuning now would be tuning against a target that is still moving. What this entry does is put the number on record before E5 is built, and name the dials nearest to it for the pass: `upkeepPerHero` (20), which is what makes a large Roster expensive; `rosterCap` (12), which is how large it may get; and `applicantFeeBase`/`applicantFeePerCalibre`, which are the least likely of the three to matter — joining fees run at 78–92 coin a year against Upkeep of 8,857, so the fee is a rounding error and the *place* is the whole of the cost. The question for the owner is whether a Roster at the cap ought to be survivable at all, or whether twelve is meant to be a size a Guild reaches late and briefly; the design's "six to twelve active" suggests the former, and `upkeepPerHero` is the dial that would answer it.

Two smaller measured facts. **Returners are all but unreachable under a policy that recruits**: 0.008 taken back per Career with the Hall, and 0 across the 200 fixture seeds of `engine/tests/e4-gate.test.ts`, because a Guild that keeps a full Roster hardly ever loses anybody to a Departure — which is DL-17 §5's finding about E2's headline mechanic showing up again from the other side. The mechanism is proved deterministically instead, by `engine/tests/returning.test.ts`, which constructs the Departure rather than waiting for one. And **the un-helped baseline is now measurable**, which closes the gap DL-17 §2 opened: the first arm above is E3 with neither the Hall nor Applicants, and it is the number any later pass should compare against.

## DL-20 — E4 verification: recruiting is a decision with a sweet spot, a ledger that counts people, and four questions left open

**Status:** Accepted · **Date:** 2026-09-19 · **Decided by:** an agent, under the owner's standing instruction to build to the plan and to record what independent verification turns up. **§1–§2 are decisions taken in this same change.** **§3–§9 are MEASURED FACTS or OPEN QUESTIONS FOR THE OWNER, each carrying a recommendation where one is due; nothing in them has been built or changed.**

**Context.** A second independent verification of E4, this time played at fleet scale rather than read line by line, found one defect in the ledger, one front-end finding that nags a player about people nobody can take on, a genuine answer to the alarm DL-19 §12 raised about recruiting to the cap, and a set of measured facts and open questions the balance pass and E5 should start from.

**Decision.**

1. **`ledger.returners` now counts returners taken on, not every offer of one (finding C7).** As built, `arriveApplicants` incremented `returners` on every OFFER of a former Hero in a batch — offer, expire, offer again — so one person who walked out, was offered repeatedly and was never accepted could run `returners` up into double figures for zero actual returns. Measured directly: one Hero walks out, and at `returnAsApplicantChance: 1` is offered seven times across 200 Days before ever being accepted (`engine/tests/returning.test.ts`, "one person offered again and again, never accepted"); before this fix `ledger.returners` read 7 for a Roster nobody had rejoined. The ledger sits beside `applicantsSeen` and `applicantsAccepted`, both of which count a person-event exactly once each, and `engine/tests/e4-gate.test.ts` already conceded the reading by comparing with `>=` rather than `===` against the count of `HeroJoined` events carrying `formerHeroId`. `returners` is now incremented in `acceptApplicant`, beside `applicantsAccepted` and guarded by `applicant.formerHeroId !== undefined`; the old count is kept under a new field, `returnersOffered`, incremented where `returners` used to be, so nothing measurable is lost, only correctly named. Both fields are documented on `CareerLedger` (`engine/src/types.ts`), filled on load exactly as `applicantsSeen`, `applicantsAccepted` and `returners` already are (`engine/src/save.ts`'s `checkLedger` and `fillFieldsAddedLater`, defaulting a document that lacks it to zero), reflected in architecture §3 and this epic's §4 State block, and `engine/tests/e4-gate.test.ts`'s comparison is tightened from `>=` to `===`.
2. **The Applicant cue no longer nags about people nobody can take on (finding C2).** At a full Roster, `applicantOffers` refuses every waiting offer, yet the CLI's `applicantCueLines` and the web's cue and `Applicants (N)` button said the same thing they say when somebody genuinely can be taken on — roughly seventeen invitations a year, in a played Career, into a view where every Accept is disabled. The view stays reachable, because a player may still want to read who is at the door, but the cue now says plainly that none of them can be taken on, and why in a few words, reading `offer.refusal` rather than recomputing "full" or "cannot afford" in a front end (`RosterFull` and `InsufficientCoin` are the only two codes reachable while somebody is actually waiting; where a mix of codes were ever possible the cue says only that none can be taken on just now, inventing no rule). In `web/`, the logic lives in `state/selectors.ts`'s `applicantCue`, which is the one place allowed to import an engine value; `Shell.tsx` only renders what the selector hands it. Wrapped, not clipped, on both front ends, and the web text wraps at 320px with every tap target still at least 40×40.

3. **Recruiting is a genuine decision, not a trap — DL-19 §12's alarm is an artefact of accepting to the cap.** Verifier's measurement: Roster-target policy (accept only while Roster < T), authored content, Hall-buying on, `bestFirst` two at a time, 120 seeds each, twenty years:

4. **The flood of Applicants**, faithful to the spec's numbers: a Guild held at four sees about 1,922 people over a Career and takes one — below `rosterFloor` the cadence doubles AND the batch is forced to maximum, and that relief never switches off; at T=8 about 761 seen, 5.7 taken; at T=12, 95% of batches arrive when nobody can be taken on. `advanceUntilAttention` never once stopped for an arrival that a Board refresh was not already stopping for, across 120 Careers — DL-19 §4 vindicated. 5. **Open: a clamped returner is cheaper.** A returner's Stats are never rewritten (right), but their reported calibre, and so their asking fee, is clamped by `maxCalibre`: a calibre-3 veteran returning to a Standing-0 Guild asks 80 coin, not 160. Barely exploitable — a player cannot choose their own Standing when a returner knocks, and the place on the Roster, not the fee, is the cost. Recorded as an oddity; **recommendation: leave.**
6. **Open: accepting an Applicant and buying a Hall improvement in the CLI take one bare keypress**, while insisting (E2) takes two and declining takes `d <n>` "so the two cannot be confused by a slip of the finger" — which protects the free action and not the 80–250 coin one. **Recommendation:** a y/n confirmation on both coin spends, decided in E7, which reworks those CLI modules. The web client has labelled buttons and no such hazard.
7. **For E6 — the "no event payload contains a space" assertion cannot be written as E6-S2 states it.** Five fields already carry spaces, only two of them E4's: `HeroRegardForGuildmasterChanged.reason` (E2, engine-authored English), `PatronRegardChanged.reason` (E1, engine-authored English), `CareerStarted.guildName` (E1), `HeroJoined.name` (E4's own spec §4), `ApplicantDeclined.name` (DL-19 deviation), plus `CareerEnded.reckoning.favouritePatron.name`. Names are data about the world, not authored prose. E6 must define the assertion as "no AUTHORED prose": exempt `name` / `guildName` fields by name, and raise the two `reason: string` fields as their own decision — they really are engine-authored English of the kind ADR-0002 forbids, and the honest fix is to make them ids, as `HeroDeparted.reason` already is.
8. **The Standing call-site test is a spelling check, not a dataflow check.** It catches a direct `standing(`/`standingOf(` call added or removed anywhere in `engine/src` (whole-map equality). It does NOT catch an alias (`const x = standingOf`), a hand re-derivation of the mean, or laundering through `maxCalibre(career)` — which IS Standing by another name and is legitimately read in `applicant.ts`. It guards against forgetting, not against evading. Recorded so nobody mistakes it for more.
9. **The contract suite tests a world no player will play.** The automatic policies deliberately do not recruit (DL-19 §10), preserving the un-helped baseline DL-17 §2 asked for. The price: only the E4 gate, its smoke and `engine/tests/e4-verification.test.ts` play full Careers with recruitment. **Recommendation:** the balance pass adds one ASSERTING fleet arm with recruitment on (a Roster target near 8), so the un-helped baseline stays a deliberate control rather than the only thing measured.

**Consequences.** §1 and §2 are built and pinned: `engine/tests/returning.test.ts` and `engine/tests/e4-gate.test.ts` for the ledger, `cli/tests/display.test.ts` and `web/tests/applicants.test.tsx` for the cue, and `web/e2e/applicants.spec.ts`'s full-Roster and unaffordable states now assert the new wording rather than merely tolerating it. Nothing DL-19 decided is disturbed beyond the ledger's two fields and DL-19 §8's own count of exports, corrected in place because DL-19 was itself written in this same uncommitted change and had not yet been accepted by the owner. §3–§9 change nothing in the game: they are read for the deferred balance pass (DL-15 §3) and for E5, E6 and E7 as named above.

**E5 must know**, from this verification pass:

- **Id namespaces already taken:** `a<n>` Applicants, `h<n>` Heroes, `pa<n>` Patrons, `r<n>` Rivals, `c<day>.<n>` Commissions, `p<day>.<n>` Parties. Rival Heroes need a namespace of their own, because ages derive from `"<seed>:age:<id>"` (DL-16 §1) and two people sharing an id would share a birthday.
- **A moved Hero's age is CARRIED, never re-derived** — the same rule DL-19 §6 gave a returner applies to any Hero E5 moves between Rosters.
- **The derived-stream pattern, and its trap.** A stream's KEY is fixed by what it is derived from, but its CONSUMPTION is not: a conditional that skips a draw (`rng.between(1, 1)` draws nothing; `shortHanded ? max : rng.between(…)`) silently reshuffles every draw after it on that stream. Draw unconditionally wherever a Rival's Roster must stay stable across differently-played Careers.
- **Flat numeric config only**, added to `CONFIG_ADDED_LATER`, and EVERY new field pinned at a non-default value in a test — two E4 fields were not, and a literal would have passed silently.
- **`calibre` lives on `Applicant` only.** E5 carries it onto `Hero`, with `calibreOfStats` and `applicantFee` already exported for exactly that (DL-19 §8, corrected above).
- **`acceptApplicant` does six bookkeeping operations by hand that E5's `moveHero` must share:** remove from `applicants`; remove from `formerHeroes` if a returner; push to `roster`; seed `regardFor` BOTH ways with `??=`; seed the Guildmaster's own `regardFor`; and set `joinedOn` / `lastCommittedOn` / `regardDecayedOn` to the current Day.
- **The Standing call-site test lists every file in `engine/src`**, so a new file E5 adds must be put in its `ALLOWED` or `MUST_BE_SILENT` list or the test fails on sight of it, correctly.

Finally, the E4 status line in [`E4-recruitment.md`](epics/E4-recruitment.md) and the E4 row in [`epics/README.md`](epics/README.md) now read "Built and independently verified 2026-09-19 (DL-19, DL-20)".

## DL-21 — The E5 rules as built: a Rival's people drawn from a stream of their own, employer Regard made exclusive by the types, one `moveHero` for every direction, and a Board rule that is E1's to the draw until somebody is wronged

**Status:** Accepted · **Date:** 2026-09-19 · **Decided by:** an agent, under the owner's standing instruction to build E5 to the adopted defaults in [E5 §3](epics/E5-rivals.md#3-known-unknowns--adopted-defaults) and to record only what the plan left open or what the build deviates from

**Context.** [E5](epics/E5-rivals.md) §4 states most of the epic exactly — the config fields, the state, the events and the API — and §3 adopts its own defaults, including the **−3** Rival Regard per Poaching that supersedes INPUTS 6.3's −5. Building it against E2, E3 and E4 as they were actually built turned up fourteen places where the plan is silent, or where following it literally would break something already standing. [DL-20](#dl-20--e4-verification-recruiting-is-a-decision-with-a-sweet-spot-a-ledger-that-counts-people-and-four-questions-left-open)'s "E5 must know" list named seven of them in advance; this entry settles those and the rest.

**Decision.**

1. **A Rival's Roster is drawn from a stream derived from the Career's seed and that Rival's id; churn from one derived from the seed and the Day; retaliation from no stream at all.** `"<seed>:rival:<rivalId>"` and `"<seed>:rival-churn:<day>"` seed throwaway xoshiro states exactly as `startingAge` and a batch of Applicants do (DL-16 §1, DL-19 §1), and **nothing in E5 draws from `career.rng`**. Four things follow, and they are the whole reason for it. World generation is bit-identical to E4's, so every seeded expectation E1 to E4 pinned still holds — `engine/tests/rivals.test.ts`'s "takes not one draw from the Career's own generator" proves it by generating the same seed with Rival Rosters and without, and comparing the generator state, the Roster, the Patrons and the Board. Churn cannot shift the Beats of a Commission resolving the same Day (`churn.test.ts`: "takes no draw from the Career's own generator"). Loading the same save twice gives the same Rosters, by construction rather than by care. And a loaded E4 save gets the Rosters a Career on that seed would have had, which is what E5's definition of done asks for — **this is a deviation from the letter of E5 §5**, which says population at load "draws from the Career's own serialised RNG state". A derived stream satisfies the intent that clause states ("so the same save always produces the same Rosters") more robustly: drawing from the shared stream would put a loaded Career on a different random path from an unloaded one, which is the very defect DL-16 §1 avoided for ages.

   The trap DL-20 named is real and was designed around. A derived stream's key is fixed but its consumption is not, so a Rival's calibre is drawn with **one unconditional `float()`** (`drawCalibre` in `people.ts`) rather than `rng.between(1, ceiling)`, which draws nothing at a ceiling of one; and churn takes both of its draws for every Rival before deciding anything, so a Rival who churns cannot shift the draws of the Rivals after them. An Applicant's calibre is deliberately **left** on E4's `between`, because every pinned id and calibre in E4's suite is that draw and the two streams need not agree.

2. **A Rival's Hero is `<rivalId>h<n>`, from a monotonic counter on the Career.** `Career.nextRivalHeroNumber` starts at 1, is serialised, and only ever goes up, so `r1h3` can never collide with an Applicant's `a<n>`, a Hero's `h<n>`, a Patron's `pa<n>`, a Rival's own `r<n>`, a Commission's `c<day>.<n>` or a Party's `p<day>.<n>`, and never repeats within a Career however much a Roster churns — which matters because ages derive from `"<seed>:age:<id>"` and two people sharing an id would share a birthday (DL-16 §1, DL-19 §2). It is filled on load from one past the highest such number the document carries, wherever the person is standing, because a Transfer brings the id across with them. **A person keeps their id when they move**, in every direction, which is what keeps other Heroes' `regardFor` attached to one person and the history readable.

3. **The employer Regards are exclusive, and the types say so.** E5 §4 sketches one optional `regardForRival?` on `Hero`; one optional field cannot make the exclusivity honest, because a Hero would then be able to hold both and a Rival's Hero would still be required to hold a Regard for a Guildmaster who does not employ them. As built there are two sibling interfaces over one shared `Person` base: `Hero` carries `regardForGuildmaster: Regard` and `regardForRival?: never`, `RivalHero` carries `regardForRival: Regard` and `regardForGuildmaster?: never`, and `AnyHero` is the union for the handful of rules that are deliberately the same in both directions. Neither is assignable to the other and neither field can be assigned on the wrong one — four `@ts-expect-error` lines in `engine/tests/rivals.test.ts` fail the build the moment that stops being true — and 200 played Careers prove no person anywhere ever holds both or neither. `Hero` keeps its name and its required field, so **not one line of E1 to E4's engine or of either front end had to change** for it. `employerRegard(career, heroId)` is the only reader the movement rules use; E2's own rules go on reading `regardForGuildmaster` directly, which is correct, because they concern your Roster and nobody else's.

4. **One `moveHero`, and `acceptApplicant` refactored onto it.** `moveHero(draft, person, from, to, regard)` in `rival.ts` is the only place in the engine a person changes employer: it takes them out of wherever they were (`applicants`, your Roster or a Rival's), out of the Guild's record of people who left, builds them holding Regard for their new employer and for nobody else's, seeds `regardFor` both ways with `??=` against the destination Roster, fills the Guildmaster's own map, sets E2's three timers to the Day, and pushes. `acceptApplicant` calls it with `from: 'applicants'`, and **every E4 test passed unmodified**, which is the condition DL-20 set for refactoring rather than sharing pieces. `content/tests/e5-one-move.test.ts` is the static guard: exactly two `guild.roster.push(` sites exist in the whole engine — world generation dealing the opening Roster, and `moveHero` — and `poachRegardThreshold` is compared in exactly one place, inside `isPoachable`.

5. **The order at a Board refresh: Retirement, drift, the Departure Check, Rival Retirement, retaliation, churn, and then the Board.** Your Roster settles first, in exactly the sequence E2 and E3 fixed, so nothing either of them pinned moved. Retaliation comes after all three: a Rival can only take somebody the Guild still has, never one who has just retired (Retirement ends well — DL-16 §7) and never one who was already walking out (a Departure is the player's own failure, not a Rival's success). It comes *after* drift on purpose — a Hero the drift has just soured is takeable in the same refresh, because Regard is what defends a Roster and the player has had the whole of the fall to watch. Churn comes last, so a Rival who has just gained somebody is at the size churn then reads. A Hero away on a Commission is settled on their return Day, for all four, on E2's own cadence (DL-14 §4). Pinned by `engine/tests/retaliation.test.ts`'s "the order the settling runs in at a Board refresh".

6. **The Board rule in its E5 form takes E1's draws exactly when nobody is soured.** `takesThisRefresh` is `clamp(rivalTakesPerRefresh + souredRivalExtraTakes × soured, 0, rivalTakesMax)` and takes no draw; the taker is `rng.pick(soured.length > 0 ? soured : rivals)`, which is **one `pick` either way** — a soured Rival is *preferred*, which is a narrower pool and not an extra draw. So a Career in which no Rival has been wronged unfolds bit for bit as it did before E5, and E1's own tests pass unmodified. Pinned by `engine/tests/churn.test.ts`: "is exactly one a refresh with nobody soured, which is E1's rule to the draw", and "costs up to three a refresh once two Rivals are soured, and is capped there".

7. **Retaliation is bounded by room and by nothing else.** A soured Rival whose own Roster is already at `rivalRosterMax` has nowhere to put anybody and their attempt finds nothing. That is a rule E5 §4 does not state, and it is what keeps `rival.roster.length <= rivalRosterMax` a genuine invariant on every Day rather than something churn has to tidy up afterwards.

8. **Where churn's people come from and go.** Somebody churned **in** is made exactly as a Rival's opening Roster is made — a fresh id, an age derived from it, a calibre drawn against that Rival's stored Standing — a person the player has never met, taken on by a Guild the player does not run. Somebody churned **out** is the one who thought least of the Rival employing them, ties broken by id: E2's Departure seen from the other side, and no draw is taken for it. They leave the **world**, not into `guild.formerHeroes`: that is the player's own history (ADR-0003), putting somebody else's people in it would inflate the reckoning's `heroesLost` and `heroesRetired`, and keeping every Rival's past employee would grow a save without bound over twenty years. `RivalRosterChanged` and the event stream are where the world's memory of them lives. The same is true of a Rival's Hero who retires — which is why narration says "somebody at another Guild has had enough of it" rather than naming a person the Career no longer holds.

9. **The precedence when several refusals hold at once: `regard`, then `heroRegard`, then `rosterFull`, then `coin`.** The obstacle hardest to shift is named first, so a player is never told to find fifty coin for somebody who was never going to come. The first two are exclusive by construction — a Transfer needs the Rival's consent and never the Hero's, a Poaching needs the Hero's disaffection and never the Rival's consent. Pinned by `engine/tests/transfer.test.ts`: "reports the one that is hardest to shift, where several hold at once".

10. **Four more `GameConfig` fields than §4 names, and one selector more than §4 names.** `rivalHeroRegardMin` (−3) and `rivalHeroRegardMax` (+2) are the band one of a Rival's own Heroes starts at: without them nobody a Rival employs is ever poachable and E5-S3 is unreachable in play, and a literal in rules code is a defect (invariant 8). `rivalStartingRegard` (0) is "starts neutral" named, for the reason DL-19 §5 named `joiningRegardAmongHeroes`. `rivalChurnGainChance` (0.5) is churn's direction inside the bounds, which would otherwise be an unnamed coin flip. ~~Every one of the eighteen E5 fields is pinned at a **non-default** value by a test, which is the hole DL-20 found in E4.~~ **Corrected in place ([DL-22](#dl-22--e5-verification-names-nobody-shares-a-roster-that-shows-who-can-be-taken-and-what-rivals-actually-cost) §10), because this entry has not been accepted by the owner: that was false for two of the eighteen.** `rivalHeroRegardMax` and `souredRivalExtraTakes` had no test driving them off their defaults, which is the very hole DL-20 §4 told E5 to avoid. The verifier closed both, and every one of the eighteen is pinned at a non-default value now: `engine/tests/e5-verification.test.ts`'s "draws a Rival Hero's Regard against rivalHeroRegardMax, not the number it defaults to" and "adds souredRivalExtraTakes for each soured Rival, under a cap that does not swallow it". The selector is `rivalOffers(career, rivalId)`, with `rivalHeroOffer` and `moveRefusal` beside it: both fees and both refusals for everybody a Rival employs, asked before the coin is spent, so no front end decides for itself what "they will not deal with you" means — the rule DL-18 followed and [E7 §4](epics/E7-terminal-ui-and-saves.md#4-technical-notes) states.

11. **Two event members more than §4 names, and neither changes an existing shape.** `RivalRegardChanged` mirrors `PatronRegardChanged` and `HeroRegardForGuildmasterChanged` exactly, so that **every** Regard movement in the game arrives as an event carrying the delta that actually landed after clamping. It is emitted only where nothing else tells it — a Vignette's `rivalRegard` Consequence — because `HeroPoached` already carries what a Poaching cost, and one fact is told once (the pattern E3 set with `TraitGained` and `HeroInjured`, DL-16). `TransferRefused` carries §4's four reasons, ordered by §9 above.

12. **A Rival's Heroes hold no `regardFor` for one another.** Nothing in the game reads the Regard between two people a Rival employs — Rivals run no Beats, compute no Backing and lose nobody to a Departure Check (E5 §0) — so it would be state that could never be seen, acted on or moved, and it would be carried in every copy of every Career, which is the one place a Rival's Roster could genuinely cost something. Somebody who crosses onto your Roster is seeded fresh opinions of your Heroes, which is the truth of it: they have not worked with them. Somebody a Rival takes keeps every opinion they had of yours, because that is a person's memory rather than a Roster's bookkeeping.

13. **`deserialiseCareer` gains an optional second argument.** Populating a Rival's Roster needs names and Backgrounds, and architecture §6 gave `deserialiseCareer` one argument. As built it is `deserialiseCareer(saved, content?)`: with content, a Rival written before Rivals had people is populated at load; without it — which is every existing caller and the whole round-trip suite — the Career loads exactly as before and is populated the first time the engine is handed content, at the top of `advance` or `advanceUntilAttention`, **before a single Day is stepped**. Both call one idempotent `populateRivalRosters`, guarded on `nextRivalHeroNumber === 1` so that a Rival whose Roster has since been emptied by play is left alone rather than refilled behind the player's back. A Rival with no opinion of your Guild is filled at `rivalStartingRegard`, so nobody is soured on the first Day after a load and nothing about the Board changes under the player (DL-15's care).

14. **`Hero.calibre` is filled on load from the Stats a person already has**, by `calibreOfStats` — the same rule a returner's calibre is read back off (DL-19 §7) — so nothing is generated, nothing is drawn, and the fill is the same number every time the document loads. `acceptApplicant` sets it from the Applicant's own calibre and `HeroJoined.calibre` is read off the **Hero**, so the field and the event cannot disagree. `ledger.heroesTransferredIn`, `heroesPoachedIn` and `heroesPoachedFromUs` each count people once, which the 200-seed smoke checks against the event counts and against the ids being distinct — the naming defect DL-17 §6 and DL-20 §1 each found once.

**Consequences.** Nothing E1, E2, E3 or E4 pinned moved, and no assertion was loosened. Six existing test files changed, all of them listed here with the reason:

- `engine/tests/decay.test.ts` — `DRIFT_ALONE` gains `rivalChurnChance: 0`, for the third time for the reason E4 added `applicantsEveryDays: 0`: that file measures one rule, and a `RivalRosterChanged` arriving at a Board refresh is another one happening in the middle of the count. A rule switched off, not an assertion weakened.
- `engine/tests/e3-gate.test.ts` and `engine/tests/e3-verification.test.ts` — the comparison of `ledger.heroesRetired` against the count of `HeroRetired` events is scoped to the Heroes who retired out of the **player's** Roster. A Rival's Hero retires by the same rule and emits the same event (E5-S1), and that ledger field has always counted the player's own people; the scoped comparison is a sharper claim than the one it replaces, not a weaker one.
- `engine/tests/save.test.ts` — the one-field-at-a-time corruption sweep gains a sixty-second timeout. E5 put a Roster on each of four Rivals, so a fully populated save carries some twenty-five more people and the sweep grew past Vitest's five-second default. Nothing it asserts changed.

## DL-22 — E5 verification: names nobody shares, a Roster that shows who can be taken, and what Rivals actually cost

**Status:** Accepted · **Date:** 2026-09-20 · **Decided by:** an agent, under the owner's standing instruction to build to the plan and to record what independent verification turns up. **§1–§2 are decisions taken in this same change.** **§3–§10 are MEASURED FACTS or OPEN QUESTIONS FOR THE OWNER, each carrying a recommendation where one is due; nothing in them has been built, tuned or changed.**

**Context.** A second independent verification of E5, played at fleet scale and read against the epic's own evidence notes, found one defect in how people are named, one thing the player is never shown about their own Roster, three citations that do not show what they claim, one conditional draw of exactly the kind [DL-20](#dl-20--e4-verification-recruiting-is-a-decision-with-a-sweet-spot-a-ledger-that-counts-people-and-four-questions-left-open)'s "E5 must know" warned about, and a set of measured facts about what Rivals actually cost a Career. [DL-21](#dl-21--the-e5-rules-as-built-a-rivals-people-drawn-from-a-stream-of-their-own-employer-regard-made-exclusive-by-the-types-one-movehero-for-every-direction-and-a-board-rule-that-is-e1s-to-the-draw-until-somebody-is-wronged) was written in this same uncommitted change and has not been accepted by the owner, so the one factual error found in it is corrected in place rather than superseded, and named in §10 below.

**Decision.**

1. **Two people the player could meet never share a name (finding F6).** As built, an Applicant's name avoided the ids in use, your Roster's names and the names of whoever else was at the door — and **not** the names of the twenty-four-odd people E5 put on Rival Rosters, nor the Guildmaster's. A Rival's own generator was the other way about: it avoided your Roster and every Rival's, and not the door. Measured over sixty played Careers on a pool the size of the shipped one, with a policy that recruits: **every one of the sixty** passed through a state in which two living people answered to one name, over **3,845 distinct pairs** — a Garrick of yours and a Garrick at The Kestrel Guild being the commonest shape of it. As built there is now **one** definition, `namesInUse(career, door)` in `engine/src/people.ts`, used by `applicant.ts` and by `rival.ts` alike: the **Guildmaster**, everybody on **your Roster**, everybody on **every Rival's Roster**, everybody **waiting at the door**, and every former Hero who **walked out** — they may knock again and must come back under their own name, which is the one case where a name must be reused rather than avoided. **The dead and the retired do not count**: neither ever comes back (`couldComeBack` offers a Departure and nothing else), and reserving their names for the length of a twenty-year Career would drain a seventy-name pool for the sake of somebody nobody will meet again. After the change, the same sixty Careers hold **no** such pair at any observed state but the one named below, and the run asserts the plain-name pool was never used up so the question stays an honest one (`engine/tests/e5-verification.test.ts`, "gives sixty played Careers no two living people who answer to one name").

   **The door is the one part of it a Rival's generator must not read, and that is not an oversight.** Declining an Applicant and ignoring one must give the same Career (E4's definition of done, DL-19 §1, asserted by `engine/tests/e4-verification.test.ts`'s "makes declining and ignoring the same Career, to the Day and the coin"), and the two worlds differ in exactly one thing: whether a name is still sitting in `career.applicants`. A Rival's churned-in Hero reading that would take a different name depending on a decision the player made about somebody else entirely, and every Rival Roster in the save would then diverge from that Day on. **This was checked and not assumed:** letting a Rival's generator read the door breaks that claim on the first seed it is tried on. So `namesInUse` takes the door as an argument — `'with-the-door'` for a batch, `'without-the-door'` for a Rival's own generator — with the reason written on the function. The defect F6 actually measured is closed either way, because it is the **Applicant** side that was blind to Rival Rosters and to the Guildmaster.

   **What that leaves, stated plainly.** One shape of collision survives, and only one: somebody a Rival hires while a person of that name is standing at your door. Over the same sixty Careers it arises 211 times against the 3,845 before, it goes away with the person when nobody takes them on, and it outlived the wait — becoming two people in work sharing a name — **4 times in sixty twenty-year Careers**, under a policy that takes on everybody it can afford. The fleet test asserts that this is the **only** shape left, by id (`a<n>` against `r<n>h<n>`), rather than counting collisions and shrugging at them. Closing it properly needs either a Rival's generator to read the door, which costs E4's definition of done, or a name reserved on the Career for the length of a batch's wait, which is new state and a `formatVersion` bump. **Recommendation for the owner:** leave it until that bump, and close it there beside §7.

   **Not one draw moved.** A name is picked with `rng.pick` over a filtered array, and `rng.pick` costs exactly one draw whatever the array's length, so widening the set changes **which** name is drawn and never **how many** draws are taken: ids, calibres, Stats, Backgrounds, ages, Regards and everything after the name on the same derived stream are bit-identical, which `engine/tests/applicants.test.ts`'s "widening the names a batch must avoid moves the names and nothing else" pins batch by batch. World generation of the player's own Roster draws names by **splicing a mutable pool** in `world.ts` and never calls `freeName` at all, so `newCareer`'s use of `career.rng` is untouched and every E1–E4 seeded expectation holds unmodified. Rival Rosters are filled in `career.rivals` order, which is the order they were generated in and the order a save preserves — id order — so a Rival's names may depend on the Rivals before them and never on anything the player did.

   **And `freeName` now tells the truth.** Its doc comment promised "a name nobody in this Career is already using" while the function fell back to a name in use once the pool was exhausted. The comment now says what actually happens, and the fallback searches every first name against every epithet in content order, taking **no further draw**, before it gives up and hands back a duplicate — which at the shipped seventy names and thirty-six epithets is unreachable, and which `engine/tests/applicants.test.ts`'s "hands back a name somebody already answers to only when every combination of the pool is taken" reaches deliberately with a pool of one name and no epithets.

2. **The player can now see the line at which their own Heroes become takeable (finding C9).** E2's risk table and E5 §0 promise that "Regard is what defends your Roster" and that "a Hero never departs from a Regard the player has not watched fall". Both front ends showed each Hero's Regard and the reason it last moved, and neither marked `poachRegardThreshold` (−2) — which sits one point **above** `refusalRegardThreshold` (−3), so a Hero at exactly −2 can be taken by a soured Rival without ever entering the band in which the Departure Check lets the Guildmaster talk them round. A player reading a Roster of −1s and −2s could not tell which number was the cliff, and a player who never poaches at all still loses 4.61 Heroes a Career to retaliation (§4 below). One read-only selector is added — `retaliationRisks(career): { heroId, regardValue, rivalIds }[]`, E5's, exported from `engine/src/index.ts`, documented in architecture §6 and added to E7 §4's list — answering, for **your** Roster, who could be taken by another Guild as things stand and by whom. A Hero appears exactly when `isPoachable(hero.regardForGuildmaster, config)`; `rivalIds` lists the Rivals both soured enough to try and with room to put somebody, and an empty `rivalIds` means takeable in principle with nobody presently minded to try. It shares `retaliate`'s own predicates rather than restating them — `isPoachable`, and `isRetaliating` and `hasRoomForAnother`, the last two lifted out of `retaliate` in this change — so the selector can never disagree with what the engine then does, which `engine/tests/retaliation.test.ts`'s "predicts exactly who the next refresh takes, over a fleet" holds it to. `hasRoomForAnother` is exported beside the selector, because the second half of this is a claim about a Guild with nobody of yours to take; `isRetaliating` stays internal, nothing outside the engine needing it. The CLI Roster and the web Roster pane mark such a Hero **in words**, never by colour alone, and name the Guilds minded to try; and, from finding C7, the Rivals view now says of a wronged Guild whether they have room to take anybody at all, from the engine's own predicate — a soured Rival at `rivalRosterMax` is completely harmless and nothing said so. **No threshold, no order of settling and no rule is changed by any of this. It is visibility only.**

3. **Poaching is effectively free and strictly dominant.** `refreshBoard` runs at the END of `stepDay` and takes only from Commissions still on the Board; the player commits between engine calls; so a player who claims every Commission before the refresh Day is immune and no Patron Regard is docked. 120 seeds per arm, authored content, twenty-year Careers, the policy deals before recruiting:

So the price of Poaching is paid only by those who did not need to poach, and Transfers are worse than not dealing at both sizes. E5 §5's risk table feared exactly this. Dials nearest to it for the balance pass: `rivalTakesPerRefresh` reaching *posted* rather than *unclaimed* work (a rule change, not made here), `transferFeeBase`/`transferFeePerCalibre`, and `poachFeeFactor`.

4. **E5 made a blameless Guild's Career much harder, through one Vignette.** `content/vignettes/the-other-guild-at-the-inn.toml` — failure −1 to a Rival the engine picks, critical +1 to another — fires **524.6 times a Career**, 6.0% of 8,804 Beats: 87.86 Regard down and 99.64 up per Career, a clamped random walk. A player who **never poaches** loses **4.61 Heroes a Career** to retaliation, where DL-21 reported 1.3–1.4. Rival Regard has no recovery rule of its own — Patron Regard has `patronRegardRecoveryEveryDays` — and recovers only when that Vignette's critical happens to pick the same Rival; with `transferConsentRegard` at 0, a single −1 closes the Transfer market with that Guild until then. For scale, and with the plain caveat that the two verifiers used different harnesses so the figures are **not** strictly comparable: DL-20 §3 measured 86.7% of Careers reaching Retirement at a Roster target of 8 before E5; this measurement gives 50.0% for the same target, never dealing. The mechanism is honest and is narrated so a player can follow it; the **rate** reads as weather, which E5 §3 names as the reason to change the rule. Dials for the pass: that Vignette's `weight` and its deltas; a Rival Regard recovery rule; `transferConsentRegard`; `retaliationRegardThreshold`.

5. **A Rival Hero's Regard for their Rival never moves.** It is written in exactly two places — generation, and `moveHero` — and **0 of 31,348 observations** differed from the value the person was generated with. 32.6% of Rival Heroes are poachable at world generation and 7.0% at the end of a Career, because churn sheds the worst-regarded first. Poaching is therefore a lookup on a draining list rather than an opportunity a player creates. **Open for the owner:** should anything move it?

6. **`poachRegardThreshold` (−2) sits one point above `refusalRegardThreshold` (−3)**, so a Hero at −2 can be taken without the Guildmaster ever being offered the talk-round the Departure Check gives. §2 makes the line visible; whether the two thresholds should coincide is the owner's.

7. **`deserialiseCareer(saved, content?)`**: when a caller omits `content`, Rival Rosters load **empty**, and every selector answers for that empty world until the first `advance` — silent wrongness rather than a refusal. It is pinned as a characterisation test, and both front ends pass `content`, so nothing shipped is wrong today. **Recommendation:** make the argument required at the next `formatVersion` bump.

8. **`docs/design.md` (~line 103) still promises a soured Rival "poaches yours harder"**; as built, and as E5 §3 adopts, a Rival at −3 and one at −5 retaliate identically — one attempt per refresh. The design document is the owner's and is **not** edited here. **Open:** build the escalation, or amend the design.

9. **Retaliation bounded by room has a pleasing emergent property.** Poaching from a Guild both sours them and makes room for them to take somebody back, so the player's own act supplies the means of the reply. It was invisible until now; §2 makes it readable.

10. **DL-21 §10's "every one of the eighteen E5 fields is pinned at a non-default value" was false for two of them.** `rivalHeroRegardMax` and `souredRivalExtraTakes` had no test driving them off their defaults — the very hole DL-20 §4 told E5 to avoid. The verifier closed both, and DL-21 §10 is corrected in place rather than superseded, because DL-21 has not been accepted by the owner. The closing tests are named there.

**Consequences.** §1 and §2 are built and pinned: `engine/src/people.ts`'s `namesInUse` and `freeName`, with `engine/tests/applicants.test.ts` and the sixty-Career fleet in `engine/tests/e5-verification.test.ts`; `retaliationRisks` in `engine/src/rival.ts`, with `engine/tests/retaliation.test.ts`, `cli/tests/display.test.ts`, `web/tests/rivals.test.tsx` and `web/e2e/rivals.spec.ts`'s "the Roster says who another Guild could take, at every width", whose evidence is `docs/verification/<project>/roster-at-risk.png` on all three device projects. **Not one seeded expectation anywhere in the suite moved**, name or otherwise: every name a test names is one it constructs by hand, and world generation of the player's own Roster never calls `freeName` at all, so the whole suite passed the names change unmodified. No id, calibre, Stat, Day or coin expectation moved either. Three pieces of evidence that did not show what they claimed are made to show it: `engine/tests/rivals.test.ts`'s and `engine/tests/league.test.ts`'s long-played fleets went insolvent on Day 70 and so never reached the churn and Retirement they cited, and now keep the Guild solvent for the whole 400 Days and **assert** that they did; two assertions that could not fail are replaced with ones that can; and `engine/tests/poach.test.ts`'s ended-Career case, which its own title claimed, is written. The conditional `rng.between(rivalRosterMin, rivalRosterMax)` in `rival.ts` — which takes **no** draw when the two are equal, the exact trap DL-20 named and DL-21 §1 says was designed around — is made unconditional; at the shipped 4–8 it moves nothing, which the whole suite passing unmodified is the proof of. `newcomerRegard`, exported from the engine and used nowhere outside `rival.ts`, is un-exported, and E5 §2's count of new API entries is corrected to **seventeen**, which is what `index.ts` and architecture §6 now both hold: the fifteen §6 already documented, less `newcomerRegard`, plus `retaliationRisks` and the `hasRoomForAnother` the Rivals view needs for §2's second half. §3–§9 change nothing in the game: they are read for the deferred balance pass ([DL-15](#dl-15--e2-verification-two-backing-constants-named-pre-e2-saves-load-without-drift-and-the-e2-measurement) §3 still defers it past E6) and for E6 and E7 as named below.

**E6 must know**, from this verification pass:

- **Four things are deferred for a Hero who is away**: Retirement, drift, the Departure Check and retaliation. `stepDay` settles them with `settling = refreshing || cameHome.length > 0` and `only = refreshing ? undefined : cameHome`. A Party that **turns back early** gets all four for free **only if** turning back merely moves `returnsOn` so that `returnParties` still yields them in `cameHome`; a second return path that bypasses `returnParties` silently loses all four. An early return landing on a refresh Day is settled exactly once only because `only` becomes `undefined` and each rule skips away Heroes. **Corrected in place by E6’s build and confirmed by E6’s verification ([DL-23](#dl-23--the-e6-rules-as-built-a-decision-is-a-moment-and-not-a-token-drawn-from-a-stream-of-its-own-a-stretch-of-days-stops-when-word-arrives-and-the-next-stretch-runs-on-and-the-liftson-means-injury-shortcut-is-closed) §5): only **three** of the four settle on the return Day. Drift does not — `decayRegard` is called under `if (refreshing)` alone, takes no `only` list, and simply skips anybody away, so what coming home restores is a Hero’s place in the **next** refresh’s drift rather than a check owed on the Day they arrive.**
- **The streams, and the trap in them.** `career.rng` is advanced only in `advance`, `advanceUntilAttention`, `commitParty` and `newCareer`; everything else draws from `"<seed>:age:<id>"`, `"<seed>:applicants:<day>"`, `"<seed>:rival:<rivalId>"`, `"<seed>:rival-churn:<day>"` or `"<seed>:rival-regard:<partyId>:<beatIndex>"`. `rng.between(low, high)` takes **no** draw when `high <= low`, and a draw inside a branch shifts everything after it on that stream: **draw unconditionally**. E6-S2 says Decision selection "mirrors Vignette selection exactly", and Vignette selection draws from `career.rng` — so think hard about whether a Decision firing or not firing may shift the Beats that follow, and whether a stream derived from the Party and the Beat is the safer home.
- **The attention set is `PartyReturned`, `BoardRefreshed`, `CareerEnded`, `ApplicantsArrived`.** A Decision can fire on a Day none of those occurs, so `PartyAwaitingWord` needs its own member of it.
- **E6-S2's "no event payload contains a space" cannot be written as stated.** The space-bearing fields today are `HeroRegardForGuildmasterChanged.reason` and `PatronRegardChanged.reason` (engine-authored English — the honest fix is ids), `RivalRegardChanged.reason` (**content**-authored, from the Vignette), `CareerStarted.guildName`, `HeroJoined.name`, `ApplicantDeclined.name`, `CareerEnded.reckoning.favouritePatron.name`, and every Trait-name field: `TraitGained.trait`, `TraitLifted.trait`, `HeroInjured.trait`, `InjuryLifted.trait`, `HeroScarred.trait`, `CommissionRefused.trait?` and `BeatResolved.slots.trait?`. Write the assertion as "no **engine-authored English**", exempting names and Trait names by field, and raise the `reason: string` fields as their own decision.
- **DL-16 §5's `liftsOn`-means-Injury shortcut is still open**, and is E6's to close **before** giving anybody a timed Trait that is not an Injury. `moveHero` now carries `traits` with `liftsOn` intact across Rosters, and `retaliate` does not exclude an injured Hero.
- **The two patterns that found this pass's holes:** drive every new config field at a value its default cannot reproduce, minding a clamp that might swallow it; and act on a Day that is not Day 1.
- **Long fleet tests need explicit timeouts.** `api.test.ts`'s 180-second one has blown under back-to-back load.

Finally, the E5 status line in [`E5-rivals.md`](epics/E5-rivals.md) and the E5 row in [`epics/README.md`](epics/README.md) now read "Built and independently verified 2026-09-20 (DL-21, DL-22)".

## DL-23 — The E6 rules as built: a Decision is a moment and not a token, drawn from a stream of its own; a stretch of Days stops when word arrives and the next stretch runs on; and the `liftsOn`-means-Injury shortcut is closed

**Status:** Accepted · **Date:** 2026-09-20 · **Decided by:** an agent, under the owner's standing instruction to build E6 to the adopted defaults in [E6 §3](epics/E6-chips-and-tacticals.md#3-known-unknowns--adopted-defaults) and to record only what the plan left open or what the build deviates from

**Context.** [E6](epics/E6-chips-and-tacticals.md) §4 states most of the epic exactly — the config fields, the state, the events and the API — and §3 adopts its own defaults. Building it against E1–E5 as they were actually built turned up thirteen places where the plan is silent, where two of its own acceptance boxes contradict one another, or where following it literally would break something already standing. [DL-22](#dl-22--e5-verification-names-nobody-shares-a-roster-that-shows-who-can-be-taken-and-what-rivals-actually-cost)'s "E6 must know" list named six of them in advance; this entry settles those and the rest.

**Decision.**

1. **The name "Chips" is historical, and there is no Chip inventory.** The epic file keeps the name the build plan gave it. The thing built is a **Decision**: a moment mid-Commission at which a Party sends word and waits, with three options and no state that outlives the answer. There is no consumable token, nothing is held between Commissions, nothing is spent, and the word "Chip" appears nowhere in the code, the content, the narration or either front end. E6 §5's risk table asks for exactly this record.

2. **Whether a Decision fires, which one, and who its slot Hero is, all draw from a stream derived from the Career's seed, the Party and the Beat — never from `career.rng`.** `"<seed>:decision:<partyId>:<beatIndex>"` seeds a throwaway xoshiro state exactly as `startingAge`, a batch of Applicants, a Rival's Roster and a Vignette's chosen Rival already do (DL-16 §1, DL-19 §1, DL-21 §1). E6-S2 says selection "mirrors Vignette selection exactly — conditions, then weight", and it does: the same predicate, the same weighted pick, the same slot filler, shared rather than copied. What it does **not** share is where the randomness comes from, and that is deliberate. A `decisionChancePerBeat` draw from `career.rng` on every Beat Day after the first would shift every Beat, every Board and every Check that follows it in **every** Career, including the great majority in which no Decision ever fires; it would have moved essentially every seeded pin in the suite. As built, a Career whose content holds no Decision, or whose `decisionChancePerBeat` is zero, takes not one extra draw from the shared generator and is bit for bit the Career E5 played. `engine/tests/decisions.test.ts`'s "takes not one draw from the Career's own generator" proves it by playing the same seed twice — once with the Decisions in content and `decisionChancePerBeat: 0`, once with `content.decisions` emptied at the default chance — and comparing the serialised Careers and the whole event streams.

   **The trap DL-20 named is answered by the shape of the key rather than by care.** The stream is fresh for **each** (Party, Beat): nothing else ever draws from it, and no later draw on it can reach another Party, another Beat or another Career. So a conditional draw inside it — the weighted pick that is only taken when a candidate exists, the slot fill that is only taken when one fires — cannot shift anything at all. The one draw that must be unconditional is the first: the chance is drawn before the candidates are filtered, so that adding a Decision to content cannot change **whether** an existing one fires, only which.

   **One interaction is real and is stated plainly.** When a Decision does fire, the Beat it displaced is resolved later — on the Day the Party is answered — and its Vignette pick and its d20 still come from `career.rng`, now interleaved differently with other Parties' Beats. That legitimately changes what follows **in that Career**, which is what a mid-Commission decision point is for. It changes nothing in a Career where no Decision fires.

3. **The tension between E6-S2's "`advance` returns immediately" and the definition of done's "a Career never deadlocks" is resolved in favour of the second, and the rule is this: a stretch of Days stops when word arrives; the next stretch runs on.** The two are irreconcilable as written — if `advance` never moves the Day while a Party awaits, the Day `timesOutOn` can never arrive, the default can never be taken, and `advance(career, 10_000)` never reaches an ending. As built:

   - A single `advance` or `advanceUntilAttention` call **stops at the end of the Day on which `PartyAwaitingWord` was emitted**, having simulated up to and including that Day and not one Day more. This is E6-S2's own acceptance box ("`advance(career, 1000)` terminates with a Party awaiting, having advanced zero Days after the stop"), met exactly.
   - A **subsequent** call, made while a Party is still awaiting, **does pass Days**. The awaiting Party is frozen — no Beat of its Commission fires and it does not come home — while every other Party, the Board, Upkeep, the Applicants and the other Guilds carry on. On the Day `timesOutOn`, the `default` option is taken, `PartyAnswered` is emitted with `byDefault: true`, and play continues. So `advance(career, 10_000)` on a Career with an awaiting Party reaches an ending, and **no caller can deadlock**, including every automatic policy written before Decisions existed.
   - It does not throw, and it is not an error: a front end ticking the clock is doing something reasonable, and E6-S2's intent — that a front end which forgets to look is not punished with an exception — is kept. What is given up is the letter of "returns immediately with no events and the Day unchanged", which is the clause that made the deadlock.

   **What this means for the front ends.** The countdown is a real countdown, so "how many Days remain before the default is taken" means something. The CLI **refuses to advance** while a Party awaits: `n` prints which Party is waiting, for how long it has waited and how many Days remain, and takes a **second** `n` before it will let the Days run — the two-keypress idiom insisting has used since E2, which is also how `cli/tests/e2e.test.ts` drives an unanswered Party to its timeout without a back door (E6 §5's risk table asks for that test). The web client disables Advance outright while a Party awaits and says why in words beside it, so it cannot pass one silently.

   **What it means for the policies already written.** `engine/tests/fixtures.ts`'s `autoPlay`, `content/tests/parse.test.ts`'s copy of it, every E2–E5 gate, smoke and verification fleet and the balance harness all loop on `advanceUntilAttention` and know nothing about answering. **Not one of them was edited.** They stop on the word, run on, and take the default on the timeout — the `pressOn` default in all three starter Decisions — and reach their endings. Most of them never see one at all, because `fixtureContent` and the verification files' own worlds ship **no** Decisions, so nothing fires there and every E1–E5 pin holds untouched. Only the authored content and E6's own test worlds carry Decisions.

4. **The displaced Beat, and the Days the waiting costs.** When a Decision fires the Day's Beat is not resolved and `party.pendingWord` is set. When the Party is answered on Day *A*, having been asked on Day *D*: `pressOn` and `sendCoin` resolve the displaced Beat **that Day**; what is left of the work is then **re-spread evenly over the Days that are left**, and `returnsOn` moves **only as far as it must** to leave room for it — `max(returnsOn, A + remaining)`. So `beatCount` is honoured and none of the remaining Beats is stranded in the past where the Day loop's `beatDays.filter(day => day === today)` would never find it again. *(Corrected in place: this sentence first read “move `returnsOn` and every unresolved Beat Day forward by A − D”, which describes the **earlier** build the Consequences below record as costing about a third of a Guild's Commissions a year. The built rule is the one stated here; independently re-measured by construction in `engine/tests/e6-verification.test.ts`, “the Beats a wait stranded”.)* Answering on the Day the word arrives therefore leaves `returnsOn` and `beatCount` exactly where they were, though the remaining Beat Days are re-spread; and leaving a Party to time out costs the Commission at most the number of Beats still to come, and often fewer — five Days of waiting with three Beats left moves the return by three, not by five. That is the price of not answering, and it is the dial nearest to "the default is doing the player's thinking for them too often" (E6 §3).

5. **Turning back goes home through `PartyReturned` and through nothing else.** `turnBack` sets `returnsOn = day + config.turnBackTravelDays`, marks the Party with `turnedBackOn`, drops every Beat Day still to come and emits `PartyTurnedBack`; the Party then comes home through `returnParties` like any other, with `succeeded: false`, the pro-rata fee, the Patron Regard of a Commission that failed and a `commissionsFailed` in the ledger. That is the whole of DL-22's first "E6 must know": **all four of the things deferred for a Hero who is away — Retirement (E3), Regard drift (E2), the Departure Check (E2) and a Rival's retaliation (E5) — settle for a turned-back Party for free**, because `returnParties` yields its Heroes in `cameHome` exactly as it always did, and an early return landing on a Board-refresh Day is settled exactly once because `only` becomes `undefined` and each rule skips a Hero who is away. There is no second return path. **One correction to DL-22's own wording, found by testing it**: three of the four settle on the return Day, and **drift does not** — `decayRegard` runs only at a Board refresh and simply skips anybody out on work, so what coming home restores is a Hero's *place* in the next refresh's drift rather than a check owed on the Day they arrive. Turning back therefore puts them back within reach of drift exactly as finishing the work would; nothing about it is special, which is the point. `engine/tests/turn-back.test.ts` tests each of the four against a turned-back Party, and the refresh-Day case against double settling.

6. **`turnBackPaysProRata: true` is built as `turnBackFeeFactor` (default 1), a number.** E6 §4 names a boolean, and `GameConfig` is flat and numeric: `deserialiseCareer` requires every field to be a number, `cloneCareer` copies it with a spread, and `--config key=value` can only set one — the three reasons DL-16 §3 gave the Hall's costs and DL-19 §3 gave the calibre budgets. A factor generalises the boolean rather than merely encoding it: the fee a turned-back Party is paid is `max(0, round(fee × turnBackFeeFactor × score / beatCount))`, so 1 is §4's `true`, 0 is its `false`, and anything between is a half-measure the balance pass can reach for. Pinned at 0.5 by `engine/tests/turn-back.test.ts`'s table test, which also pins the fee at scores 0, 1 and 3 of 4 Beats at the default.

7. **`Party.decisionUsed` stays the boolean E6 §4 names, and `decisionsPerCommission` is read as a gate rather than a counter.** A Decision may fire while `!party.decisionUsed && config.decisionsPerCommission >= 1`, so 0 switches Decisions off for a whole Career and 1 is the cap. More than one per Commission is E6 §0's own **deliberately deferred** item, so a counter would be state carrying a possibility the epic has ruled out; when that deferral is lifted the flag becomes a count, which is an addition and not a format change. Pinned at 0 by `engine/tests/decisions.test.ts`, which is a value the default cannot reproduce.

8. **`pendingWord.optionIds` holds every option the Decision offers, and `requires` is re-checked at the moment of answering.** E6 §4's comment says "only those whose requires are met", and E6-S1's own acceptance box says an option the Guild cannot afford "is offered but not selectable, and the engine refuses it by id" — which cannot be true of an option that was never offered. Coin moves while a Party waits, in both directions, so an affordability frozen at ask time would be a lie by the second Day. As built: `optionIds` is the offer, in authored order, and never changes; `PartyAwaitingWord.options[].affordable` is the state **at ask time**, because an event is a past-tense fact; and `wordOffers(career, content)` recomputes affordability against the coin the Guild holds **now**, which is what both front ends render and what `answerParty` enforces. Answering with an option the Guild cannot pay for is `EngineError('InsufficientCoin')` and a byte-identical Career; answering with an id the Decision does not carry is `NoSuchOption`.

9. **Three read-only selectors, so that no front end restates a rule** (the rule DL-18 followed and [E7 §4](epics/E7-terminal-ui-and-saves.md#4-technical-notes) states). `awaitingParties(career)` is E6 §4's own. `wordOffers(career, content)` and `wordOffer(career, partyId, content)` are the two more the front ends actually needed: for each awaiting Party, the Decision's id, the slots, the Day it was asked, the Day it times out, the Days waited and the Days left, which option is the `default`, and every option with its kind, its cost, whether the Guild can take it **now** and — where it cannot — the shortfall, as the very `EngineErrorCode` `answerParty` would throw. Neither computes anything a front end could get wrong, and neither carries a word of prose: the prompt and the labels are content, filled by `narrate`'s `wordProse`. Documented in architecture §6 and added to E7 §4's dependency list.

10. **DL-16 §5's `liftsOn`-means-Injury shortcut is closed by putting the kind on the held Trait.** `HeroTrait` gains an optional `kind`, set by `giveTrait` at the moment a Trait is given, from the `TraitDef` the content defines — self-describing state that survives a save round trip and keeps `isInjured`, `injuredUntil`, `availableHeroes`, `injuredHeroes` and `unavailableAmong` on their `(Career) => …` signatures, so neither architecture §6 nor either front end changed by a line (the E3 verifier's own recommendation, DL-22). A timed Trait is an Injury when its `kind` is `'injury'` **or** when it carries none at all, which is exactly what every save written before E6 means: DL-21 §5 records that **E5 gives nobody a timed Trait that is not an Injury**, so the fallback is not a guess but a fact about every document this engine has ever written. No load-time fill is needed or taken, and a first attempt at one was removed: it would have rewritten the Traits of a Career that had done nothing, so `advance(career, 0)` would no longer have stood still and three E2–E5 tests that compare a person's Traits before and against after would have moved for no reason at all. `liftDueTraits` still reads the TraitDef where the held Trait carries no kind, so even a Trait set by hand lifts as the content says it should. World generation, a Background's Traits, an Applicant's and a Rival's people are untouched, because none of them goes through `giveTrait`; `moveHero` carries `kind` across Rosters with `liftsOn`, and `retaliate` goes on not excluding an injured Hero. `engine/tests/timed-traits.test.ts` proves a timed non-Injury Trait does not make its holder unavailable, lifts as `TraitLifted` rather than `InjuryLifted`, is not reported as an Injury by any of the five readers, and survives a save and a move between Rosters.

11. **Two event fields more than E6 §4 sketches, and neither changes an existing shape.** `PartyAnswered` carries `commissionId` and `slots` as well as the ids §4 names, for the reason `ApplicantDeclined` carries `name` (DL-19): the option's `label` is authored prose with the same tokens a prompt has, `pendingWord` is cleared by the time the event is read, and narration would otherwise have nothing left to fill `{hero}` or `{commission}` from. Both are ids. `CoinChanged.reason` gains `'sendCoin'` under E3 §4's widening rule. The new `{ kind: 'backing'; delta }` Consequence is valid in a Vignette's outcome as well as in an option's `consequences`, because E6 §4's whole reason for adding it is that an option's `effect` and a Vignette's outcome should speak one vocabulary.

12. **E6-S2's "a test asserts no event payload anywhere in the engine contains a space" is met as amended, and the amendment is DL-20 §7's and DL-22's.** It cannot be written as stated: `HeroRegardForGuildmasterChanged.reason` and `PatronRegardChanged.reason` are engine-authored English and predate E6; `RivalRegardChanged.reason` is content-authored; and `CareerStarted.guildName`, `HeroJoined.name`, `ApplicantDeclined.name`, `CareerEnded.reckoning.favouritePatron.name` and every Trait-name field are names of things in the world. The test written is **"no event carries engine-authored English, and E6's new events carry ids and numbers only"**: it walks every string in every event payload over a fleet of played Careers, exempts by **field name** the ones that are names or content-authored, names the two engine-authored `reason` fields as a **known exemption** with a comment citing DL-20 §7 and DL-22, and asserts that no string field of `PartyAwaitingWord`, `PartyAnswered` or `PartyTurnedBack` contains a space at all — and that every Decision id and option id is kebab-case. **Turning the two `reason` fields into ids is its own decision and is not taken here**: it would change what `narrate` prints for every Regard movement in the game and it belongs to whoever owns that prose, not to E6.

13. **A Decision can fire for a Party that was already away when the save was loaded.** `decisionUsed` fills `false` and `dcDelta` fills `0`, so a Party committed before the rule existed is considered exactly as one committed today — on a Beat Day after its first, once. Refusing them would need a flag recording the engine's own history rather than anything about the world. Nothing is surprised on the first Day after a load (DL-15's care): a load fires nothing, sets nothing and draws nothing, and the first Decision that can fire for such a Party is on its next Beat Day.

**Consequences.** Nothing E1, E2, E3, E4 or E5 pinned moved, and no assertion was loosened. The `content` package gains a `decisions/` directory and nothing else; the engine gains one file, `decision.ts`, and the Day loop gains two calls into it.

**Exactly one seeded expectation in the suite moved, and it is named below with its cause.** Every other one held, and that is not an argument but a measurement. `content/tests/balance.measure.test.ts`, run with `HEROESIM_BALANCE_CONFIG='{"decisionChancePerBeat":0}'` over the same 120 seeds and the same six arms DL-21 measured, reproduces DL-21's table **to the digit** — 28.3% / 73.3% / 51.7% / 61.7% / 64.2% reaching Retirement, 44.4 / 63.6 / 178.4 / 179.6 / 179.7 Commissions per year — which is 120 twenty-year Careers × six arms saying that a Career in which no Decision fires is the Career E5 played. `engine/tests/decisions.test.ts`'s "takes not one draw from the Career's own generator" says the same thing at the byte, on four seeds, comparing the serialised Career, the whole event stream and the generator state itself.

**Seven existing test files changed, all of them listed here with the reason. Two are the exhaustive maps every new event member and every new `EngineErrorCode` forces by design; three are inventory; one is a driver; and one is the single seed that moved.**

- `engine/tests/events.test.ts` — `EVERY_EVENT` from 35 members to 38, and the count beside it.
- `narrate/tests/errors.test.ts` — `CODES` from 12 codes to 15.
- `narrate/tests/stream.test.ts` — "covers every kind of paragraph the loop can produce" names `word` and `answer` beside the seven it already named. A one-year Career over the authored content now meets a Decision, which is the point; the seven before them are unchanged, which is the half of E6-S4's box worth guarding.
- `content/tests/e4-standing-callsites.test.ts` — `decision.ts` added to `MUST_BE_SILENT`. The two lists together must account for every file in `engine/src`, so a new one has to be named or the test fails on sight of it, correctly. What the Guild's Standing has earned has nothing to say about whether a Party stops to ask.
- `web/tests/applicants.test.tsx` — its `Shell` render gains the one new prop. Inventory, not assertion.
- `engine/tests/injury.test.ts` — the Party literal it builds by hand gains `decisionUsed: false` and `dcDelta: 0`, because `Party` gained two required fields. A driver, and the only one.
- `narrate/tests/regard.test.ts` — **the one seeded pin that moved**, re-pinned from `narrate-regard` to `narrate-regard-b` at the same four years and under the same insisting policy, with the reason written on the line. This file plays the **authored** content, which now ships Decisions, and on the old seed one fires early enough to change which Commissions the policy takes — so the Hero who used to walk out inside four years no longer does. Not one assertion was touched or weakened: the new seed gives the same arc the three failing tests have always asserted — a refusal over Regard, an insistence that actually cost something, and a Hero who leaves — and it gives it with Decisions **on**, which is the shipped world, rather than by switching a rule off as `decay.test.ts` has three times. Four candidate seeds were checked and three of them carried the arc; the first was taken.

`content/tests/parse.test.ts` and `cli/tests/{display,e2e}.test.ts` **grew** rather than changed: every assertion they held still holds, and E6's are added beside them.

**This is the single biggest thing E6 does to the game, and it is not what the epic set out to do.** A Guild that never answers loses about a fifth of its Commissions a year and less than half of its Careers reach Retirement where two-thirds did. The cause is plain and is not the Decisions themselves: a Party that has sent word **stands still** until somebody answers, and nobody answering means five Days of standing still — `config.wordTimeoutDays` — on a Commission whose whole span is five to ten. At 0.476 words per Commission that is the Guild's throughput. The dials nearest to it are `wordTimeoutDays` (5) and `decisionChancePerBeat` (0.2), and the rule nearest to it is whether a waiting Party should stand still at all. **Nothing is tuned here**: [DL-15](#dl-15--e2-verification-two-backing-constants-named-pre-e2-saves-load-without-drift-and-the-e2-measurement) §3 defers the balance pass until E3–E6 are all built, and they now are, so this is the measurement that pass starts from — with the control above, which lets E6's cost be read off exactly rather than inferred.

Two smaller measured facts. **The even-handed answering policy is a deliberately bad policy**, and the figure is a measurement of what an option costs rather than of how the game plays: taking the three kinds strictly in turn calls off **15.6% of every Commission the Guild takes**, and 5.0% of those Careers reach Retirement against 24.2% for the same world answered by nobody at all. Turning back is emphatically not free, which is what E6 §5's risk table asked to be shown. And **the Days a Party waits are not charged twice**: an earlier build slid `returnsOn` forward by the whole wait, which cost about a third of a Guild's Commissions a year on its own; as built, what is left of the work is spread over the Days that are left and the Day they are due back moves only as far as it must to leave room for it (§4 above).

**The fleet work's cost in wall time.** `engine/tests/e6-gate.test.ts` is the whole of it: 200 played Careers under two policies, the no-deadlock proofs and the twelve-Career prose sweep together run in **46 s**. The rest of E6's engine suite — `decisions`, `word`, `answer`, `turn-back`, `timed-traits` — runs in under two seconds all told, because every one of them constructs the state it is about rather than playing towards it. The whole suite went from about 200 s to about 250 s.

**E7 and E8 must know.** `wordOffers`, `wordOffer` and `awaitingParties` are on E7 §4's list, and `narrate`'s `wordProse` beside them: a screen that shows a Party's options must not work out for itself what one costs, which the Guild can take, which the timeout will take or how long is left. The CLI's `n` now takes a second press while a Party waits, which is the third screen to use the two-keypress idiom and strengthens the case DL-20 §6 made for the other two. `web/src/panes/Word.tsx` is E8 §4's planned `Word.tsx`, under `panes/` beside the rest — there is still no `sheets/` directory — and it takes the Report pane's place rather than covering it, because a Party waiting is not something to be dismissed.

## DL-24 — E6 verification and the bounded balance pass: a Decision becomes rare because the design calls it a rule, a Vignette goes back to being colour, and two reads land in the engine so that E7 can keep its promise

**Status:** Accepted · **Date:** 2026-09-20 · **Decided by:** an agent, under the owner's standing instruction to build to the plan and to record what independent verification turns up. **§A1–§A7 and §B1–§B4 are decisions taken in this same change.** **§B5 is a list of OPEN QUESTIONS FOR THE OWNER, each carrying a measurement and a recommendation; nothing in it has been built, tuned or changed.** · **Amends:** DL-23's §12 exemption list and the `narrate/tests/regard.test.ts` re-seed recorded in its Consequences, corrected in place above (not superseded) because DL-23 was itself written in this same uncommitted change and has not been accepted by the owner

**Context.** An independent verification of the built E6 found six things, and asked for the one bounded balance pass [DL-15](#dl-15--e2-verification-two-backing-constants-named-pre-e2-saves-load-without-drift-and-the-e2-measurement) §3 deferred "until E3–E6 are all built" — which they now are. The pass is bounded because the same verification measured that a player who plays **sensibly** is already inside [DL-13](#dl-13--the-e1-balance-pass-commission-score-counted-once-a-wider-critical-margin-patron-regard-that-recovers-and-an-economy-where-coin-is-tight)'s accepted targets. The economy does not need rebuilding. What needed fixing is the two places where the build contradicts something the design states as a **rule**, and the only balance changes taken are `decisionChancePerBeat` and one Vignette's `weight` and `conditions`. Everything else in this entry is measured and recorded.

### Part A — what the verification found

1. **§A1 — the browser could not let a timeout happen, and the header said something false (F10).** `web/src/layout/Shell.tsx` disabled Advance outright while any Party awaited, and there was no other way to pass a Day, so a player who genuinely wanted the default still had to click it. Meanwhile the Word card said "With no word from you, this is what they will do" and the header said "the Days will not run until you answer" — true of that client and **false of the engine**, which has passed Days with an awaiting Party frozen until `timesOutOn` since E6 was built (DL-23 §3). The CLI has had the two-`n` idiom all along; the browser had no equivalent at all.

   **As built:** a deliberately secondary control in the Word pane — "Leave it to their judgement and let the Days run" — behind the **two taps** E2's insistence has used since it was built. The first tap only explains: which Parties stand still, until which Day, in how many Days, and what each will then take, in the option's own authored words. The second runs the Days, through the very `advanceUntilAttention` the main Advance calls. Any change to the set of waiting Parties disarms it, so a stale second tap cannot pass Days the player did not mean to pass. The main Advance **stays guarded**. The header now reads "Advance is held until you answer, or leave it to them", which is true of the client and of the engine alike. Logic stays in `web/src/state/` (`web/tests/engine-imports.test.ts` unchanged), the layout is CSS only, every control is at least 40×40 and the pane wraps at 320px. Pinned by six cases in `web/tests/word.test.tsx` and two Playwright tests per device project in `web/e2e/word.spec.ts`, with `docs/verification/<project>/word-leave-it.png` as the evidence.

2. **§A2 — two reads a front end needs and must not compute (F11), attributed to E6 because [E7 §4](epics/E7-terminal-ui-and-saves.md#4-technical-notes) promises to add nothing to the engine.** Both are exported from `engine/src/index.ts`, documented in architecture §6 and added to E7 §4's dependency list, and both are pure under deep-freeze.

   1. **`projectedReturn(career, partyId)`.** Both front ends showed `party.returnsOn` while a Party waited, and it is a Day that is going to slip: the Beats the waiting strands are re-spread on the Day the Party is answered and the return moves as far as it must to leave room for them (DL-23 §4). "Due back Day 10" on Day 4 quietly became Day 11 after the timeout, and nothing said so. The selector answers the earliest Day a Party can now be home, **sharing the arithmetic `answerParty` actually applies** rather than restating it: the re-spreading is lifted out of `applyOption` into one `continuationOf`, which both call. Shown as "back no sooner than …" in the CLI's Away block and in the web Roster pane, and compressed to "no sooner, *N*d" in the CLI Roster's fifteen-column Where cell, which is as much as that column holds.
   2. **`turnBackOutcome(career, partyId, content)`, and the same value on `WordOffer`'s `turnBack` option as `outcome`.** `turnBackFee` was exported, but a view would have had to assemble its four arguments itself — the fee, the **score with the option's own `score` Consequences already applied to it**, and the Beat count — which is a rule restated in a front end and DL-18 forbids it. Neither front end told the player what turning back would pay **before** they chose it. Both now say so in words, beside the option: "Calling them home pays 19 coin of the 75 the work is worth, for 1 of 4 Beats done." Coin is never abbreviated, and the sentence is word for word the same in the terminal and in the browser. A fleet test proves the figure shown is the `PartyReturned.feePaid` that then happens, across forty-eight Careers and four configurations including `turnBackFeeFactor` 1, 0.5 and 0, and a turn-back whose own Consequence docks the score.

3. **§A3 — a Decision that asserted an Injury the state did not carry, and ford prose on work with no ford in it (F12).**

   `content/decisions/somebody-is-hurt.toml` told the player "{hero} took something two days ago and has been walking on it since" while **no option gave an Injury Trait**: the Roster showed nothing, and the Hero was committable the moment they were home. An Injury is a Trait (ADR-0005), and "hurt" is on CONTEXT.md's avoid-list for that very concept. It is replaced by `content/decisions/somebody-is-flagging.toml` — **the same alphabetical position**, because content load order feeds the weighted pick — whose fiction is a long hard road and a Party worn down by it, which the state carries honestly with no Trait at all. **§B2 — `decisionChancePerBeat` 0.2 → 0.1, because the design calls rarity a rule.** The design says "RARELY, a Party sends word" and [E6 §0](epics/E6-chips-and-tacticals.md#0-what-lands-in-e6) says "rare is a rule, not a hope". **0.1 is adopted.** It puts the sensible arm at 0.210 words per Commission — one Commission in 4.8, which is the "roughly one in five" the pass was asked for — squarely inside the 0.15–0.25 band, and it is a round number a reader can hold. 0.08 sits on the floor of the band with nothing to spare; 0.12 sits near its ceiling.

**`wordTimeoutDays` is left at 5, and here is why.** The sweep above is the reason to have considered it: at the old rate a silent player reached Retirement on 61.7% of Careers at five Days against 65.8% at one, so shortening it bought about four points. But almost the whole of that gain is the *rate*, not the timeout — once a Commission stops one time in five rather than one time in two and a half, the Days a Guild spends standing still fall by nearly half on their own, and the measured sweep at 0.1 shows no consistent ordering between one, three and five Days at all. Against shortening it there is a plain design reason: `wordTimeoutDays` is the player's **thinking time**, and E6 §3 names "the default is doing the player's thinking for them too often" as the thing to watch. Cutting it to one Day would take the choice away from anybody who looked at something else for an evening. It stays at five.

**§B3 — the Vignette that sours another Guild goes back to being colour.** E5 §0 and E2 §5 promise that "Regard is what defends your Roster" and that "a Guild with no soured Heroes loses nobody", and E5 §3 names losing people "like weather rather than consequence" as the reason to change the rule. `content/vignettes/the-other-guild-at-the-inn.toml` is the only thing in the game that sours a Rival besides a Poaching, and it fired **718.1 times a Career, 6.4% of every Beat**, on the sensible arm. That is not an occasional evening at an inn; it is the main mechanism.

Two dials move, both of them the Vignette's own:

1. **`conditions.tags` from `["talk", "town", "escort", "guard"]` to `["talk", "town"]`**, which is exactly its own top-level `tags`. An evening in a taproom, with another Guild's party at the long table and a Hero saying more than they meant to, belongs to work done among people and to work that turns on what is said. `escort` and `guard` between them admitted more than half the Commissions in the game, including a night watch in a crypt and a pay chest up a mine road.
2. **`weight` from 2 to 1**, which halves its share of the pick among the Vignettes still eligible beside it.

The band is a statement about how the Check should *feel*, and two epics have changed what goes into it. Not applied either way: it would re-pin the entire suite and it is a matter of feel.

2. **Should a waiting Party stand still?** Almost the whole cost of a Decision used to be the Days a Party spends idle, and the control for it is exact, because `silent` and `default` differ **only** in *when* the same option is taken. **The cost has collapsed with the rate.** Before the pass: 61.7% → 68.3% reaching Retirement, **+6.6 points** for answering at once with the very option the timeout would have taken, and nine more Commissions a year. After it: 78.3% → **75.8%**, which is 2.5 points the *wrong* way and is noise at 120 seeds — at one Commission in 4.8 the Days a Guild spends standing still are no longer measurable against everything else that moves a Career. What is still worth six points is **choosing well**: the same player answering sensibly reaches 85.0%. The waiting is what gives a Decision its weight, and the measurement that made it look expensive was a measurement of the rate, not of the waiting. It is a rule change and is the owner's.

## DL-25 — The E7 rules as built: the starting debt is an opening deduction and nothing else, colour is applied at the output boundary so every view stays a pure function, and the words two front ends already shared move into `narrate`

**Status:** Accepted · **Date:** 2026-09-20 · **Decided by:** an agent, under the owner's standing instruction to build E7 to the adopted defaults in [E7 §3](epics/E7-terminal-ui-and-saves.md#3-known-unknowns--adopted-defaults) and to settle the questions DL-20 §6 and DL-24 §B5 hand to E7 · **Amends:** the `SlotFile` shape sketched in [E7 §4](epics/E7-terminal-ui-and-saves.md#4-technical-notes), which cannot answer the slot picker's own acceptance box as written

**Context.** [E7](epics/E7-terminal-ui-and-saves.md) §4 states the module layout and the engine reads exactly, and §3 adopts its own defaults. Building it against E1–E6 as they were actually built turned up one contradiction inside the epic itself, five questions earlier entries left for E7, and eight places where the plan is silent or where following it literally would break something already standing.

**Decision.**

1. **The starting debt lands, as one flat number read in exactly one place, and E7 §0's "nothing lands in the engine" yields to §3's adopted default — which is the contradiction, named.** E7 §0 says "E7 adds no state, no config field, no event and no engine function"; E7 §3's own table adopts "yes, `config.startingDebt: 0` exists and defaults to **0**"; and E7's definition of done says the debt "either lands here as a config field or is struck from the design in the same change". The two cannot both be honoured. §3's adopted default decides it, because an adopted default is a decision already taken and §0 is a general rule the same epic then makes one written exception to.

   What the debt **is** comes from the design: "You start with a going concern — three or four Heroes who already have history and Regard for one another, **and a debt** — rather than an empty Roster." The Guild the player inherits is not flush; its opening float has already been eaten into by what the last Guildmaster owed. So the smallest honest mechanism is an **opening deduction**, and it is the whole of it: `newCareer` opens the Guild at `startingCoin - startingDebt` coin and sets `ledger.peakCoin` to the same number, so the peak is a balance the Guild actually held rather than one it never saw. There is **no new state**, no `debt` field on the Guild, nothing owed that is tracked, no event, and no draw: `x - 0 === x`, so at the default every seeded expectation in the suite is bit-identical and the whole of E1–E6 is untouched. A standing obligation collected later would have needed state on the Career and a `formatVersion` bump; a debt taken out of the opening balance needs neither, and it is what the design's sentence actually says.

   It is visible to the player because the coin line reads `career.guild.coin`, which is the true balance from Day 1, and because `narrate` says so in the opening: the `CareerStarted` paragraph gains a clause naming the debt when `config.startingDebt` is non-zero, and says nothing at all when it is zero. The engine still carries no prose — the number is on the config the paragraph already has in hand.

   `startingDebt` joins `CONFIG_ADDED_LATER` in `engine/src/save.ts`, so every save E1–E6 wrote still loads and takes the default. It is pinned at a non-default value by a test, and its inertness is pinned two ways: the same seed played at `startingDebt: 0` and with no override at all gives byte-identical Careers and event streams, and a static scan proves `startingDebt` is read in exactly one file of `engine/src` — the same shape of guard `content/tests/e5-one-move.test.ts` already uses, living in `content/tests` for the reason DL-19 §11 gave.

2. **One read is added to the engine, and it is a re-export of something already written.** The Patrons view has to say that a Patron at the floor is posting nothing, and "the floor" is `patron.regardForGuild.value > config.patronPostsAboveRegard` — a rule, which [E7 §4](epics/E7-terminal-ui-and-saves.md#4-technical-notes) and DL-18 both forbid a front end to restate. `postingPatrons(career)` has been in `engine/src/board.ts` since E1 and is what `refreshBoard` itself asks; it is now re-exported from `engine/src/index.ts`, attributed to **E1**, which owns the Board and the Patrons. No behaviour change and no new rule, exactly as DL-18 §1 re-exported `unavailableAmong`. Documented in architecture §6, added to E7 §4's dependency list, and given its own public-API test.

3. **DL-20 §6 and DL-24's open question on bare-keypress coin spends: every coin spend now takes a confirming keypress, and the free action stays free.** Accepting an Applicant (80–160 coin plus a permanent addition to Upkeep) and buying a Hall improvement (200–250 coin) each asked for one bare press, while insisting (E2) and a Transfer or a Poaching (E5) each took two. The two verifiers' recommendation is adopted without amendment: a `y/n` confirmation on **every** coin spend. Answering a waiting Party with an option that carries a `cost` is the third screen brought into line, which DL-23 did not cover because E6 shipped before this was settled. Declining an Applicant is still `d <n>` and still free, and the asymmetry is now the right way round: the screen asks a second time when coin leaves the Guild and never when it does not. The confirmation names the cost and, for an Applicant, the Upkeep their place will cost from now on, so the second press is informed rather than ceremonial.

4. **DL-24 open question 13 — what the reckoning says about `ledger.heroesInjured`.** It counts Injuries and not Heroes (DL-17 §6), about 470 of them in a twenty-year Career at a Roster of eight, and printing it as "N Heroes injured" would be a lie about a Roster of twelve. The reckoning gains one line, in `narrate`'s `reckoningLines` where both front ends read it: `Harm: 470 Injuries and 4 Scars between them.` — counting the things given, naming them as what they are, and never as people. `Reckoning` gains no field: `reckoningLines` already takes the Career and reads `career.ledger`, which is where both counts live.

5. **DL-24's open question on the two difficulty vocabularies — one set of words, in `narrate`.** 'Gentle/Testing/Grim' in the browser and 'easy/fair/hard/grim' in the terminal are presentation words over one engine number, and neither front end should own them. `narrate` gains `difficultyWord(difficulty, config)` and `DIFFICULTY_BANDS`, and the set adopted is the terminal's four — `easy`, `fair`, `hard`, `grim` — because four bands over an eight-point range says more than three, because lower case is what a word in a value position wants, and because every assertion already written about it is the terminal's. `web/src/state/selectors.ts`'s `difficultyBand` becomes a pass-through and `DIFFICULTY_BANDS` is re-exported from it, which is the one-line swap the epic allows: no web test names either set of words, so the web suite and all 120 Playwright checks pass unmodified.

6. **`cli/src/display.ts`'s `nextDayOn` is deleted, with the test that pinned it.** DL-18 kept it unused and DL-24 left it for E7. Nothing wants it: the two countdowns are `daysUntilUpkeep` and `daysUntilBoardRefresh`, which is what DL-18 replaced its only caller with. `display.ts` itself is gone in the restructure below, so the function goes with it.

7. **The Roster view says the hedge in full, and nothing in the terminal hedges in an abbreviation any more.** DL-24 §A2a compressed "back no sooner than Year 2, Day 58" to "no sooner, 3d" because the Roster's Where column was fifteen characters. E7-S3's Roster is a whole screen rather than a row on the main one, so it says the sentence in full, stacked under the Hero; the main screen's AWAY block says it in full too, because a line of its own has the width for it. The fifteen-column form survives nowhere.

8. **Colour is applied at the output boundary, which is what lets every view be the pure function E7 §4 asks for.** E7 §4 requires `render(career, width): string[]` and no state; the CLI as it stood passed a `Palette` into every renderer, which is a fourth argument and a presentation decision taken inside the view. As built, a view returns **plain text only**, and `screen.ts` dresses finished lines on their way out by one documented rule: a line whose first non-space run is a block heading in capitals is bold, and a line of key hints is dim. Nothing else is coloured, so colour can never be the only carrier of meaning — there is no state it marks that the words do not (E7-S5). `NO_COLOR`, a non-TTY stdout and `--no-colour` each switch the dressing off entirely, and the output then contains no escape at all.

   For the same reason the **ASCII fallback is a transform at that boundary** and not a change to `narrate`: `TERM=dumb` or a non-UTF-8 locale maps the em dash, the middle dot, the minus sign and the curly quotes to their ASCII equivalents, one character for one, on every line the program prints — narration included, which is shared with the browser and must not be rewritten for a terminal's sake. `screen.ts` is the only module in `cli/` that reads `process.env` or `process.stdout`, which a test asserts by scanning the source.

9. **The slot file gains a header, because the picker's own acceptance box cannot be met without one.** E7 §4 sketches `SlotFile { formatVersion: 1; savedOn: string; career: string; history: string[] }` and E7-S4 requires the picker to list each slot's Guild name, Day, Year and Roster size "without deserialising the whole Career". Those four facts live inside the `career` string, so with that shape the picker would have to parse and read the whole document anyway. As built the file carries a fifth field: `header: { guildName; day; year; rosterSize; seed; ended }`, written from the Career at save time by one function, so the picker reads a small object and never touches the Career at all. DL-02's one-serialiser rule is untouched — `career` is still the **exact** string `serialiseCareer` returned, never re-encoded, and the browser reads that inner string unchanged — and a test asserts the header agrees with the Career it wraps for every save, so it cannot drift.

10. **A bare `serialiseCareer` string — every save E1 to E6 wrote — is read, not refused, and the definition of done requires it.** "Saves from E6 load unchanged" is a DoD item, and E6's CLI wrote the Career on its own with no wrapper. `loadSlot` looks at the parsed document: a `career` field holding a string is a slot file; a document carrying `guild` and `seed` is a bare Career, loaded with an empty history. Nothing on disk is rewritten by reading it, so this is tolerance at the boundary rather than the migration the design rules out — the file is only ever written in the new shape when the player next saves. A slot file whose **wrapper** `formatVersion` is not 1 is refused with a sentence naming the version found and the one expected, and the file is left exactly as it was.

11. **`q` and an interrupt both write the autosave slot, and a named slot is never written without being asked.** The autosave slot is its own slot and nothing else ever writes it, so it can never overwrite a Career the player meant to keep (E7 §5's risk row). Quitting from a named slot writes the autosave and then asks **once** whether to write the named slot too. An error thrown while a view is rendering is caught, the Career is autosaved before anything is printed about it, and the CLI exits with a sentence rather than a stack trace. A Career that has ended clears its own autosave, as E1 built.

12. **What the interrupt tests prove on Windows, stated plainly because an automated test will not reach the last step.** `process.kill(pid, 'SIGINT')` on Windows terminates the target through `TerminateProcess` and runs no handler, so no spawned test of that shape can prove that a real Ctrl-C reaches the program. Three things are proved by the suite: the handler itself autosaves and reports where it went, called directly; the real program installs it on `process` for `SIGINT`, asserted by listener count in a spawned Node process that loads the CLI's own module; and emitting `SIGINT` in that spawned process runs the handler, writes a slot that loads, and leaves exit code 0.

    **Corrected 2026-09-20, while E8-S6 was built.** This entry said "Not proved on Windows: that the operating system delivers SIGINT to the process on Ctrl-C", and that was wrong: delivery **is** provable on this machine, by hand, and the verifier proved it twice with no new dependency. A PowerShell that shares the child's console calls `kernel32!SetConsoleCtrlHandler(NULL, TRUE)` to deafen itself and then `kernel32!GenerateConsoleCtrlEvent(CTRL_C_EVENT, 0)`, which is a real Ctrl-C delivered by the operating system to every process on that console. The child printed `Interrupted. The Career is autosaved to …` and the slot it wrote loaded again. What is true is narrower and is why it is not in the suite: **the delivery is left out of the automated tests because it needs the runner to share and deafen a console**, and a Vitest run that deafens its own console and then raises a console-wide Ctrl-C cannot safely be run inside CI or beside other work — it would take the runner down with the child. So it is a manual check, recorded here with the mechanism, rather than a test that would pass without exercising anything.

13. **The key map, as the epic's own mock draws it, and the one binding that moved.** E7-S1's mock says `[r] roster` and `[p] patrons`; `r` opened the other Guilds from E5 and architecture §9 said so. The mock wins, because the Roster is the most-opened view in the game and E7 is the epic that draws the screen: `r` is the Roster, `p` is the Patrons, and the other Guilds move to `o` — the view is called "The other Guilds" and always has been. `g` League, `i` Hall, `a` Applicants, `f` former Heroes, `n` advance, `s` save, `l` slots, `d` delete, `h` help and `q` quit are unchanged or new. Architecture §9 is updated in the same change, and every script in `cli/tests/e2e.test.ts` with it.

14. **The history is derived by narrating a filtered event list, which is the only way to get one paragraph per moment without re-wording anything.** E7-S2 requires each entry to be "one `narrate` paragraph… never re-worded by the CLI", and a `Paragraph` carries no event type, so the paragraphs of a whole step cannot be told apart after the fact — a Hall purchase arrives as a `coin` paragraph exactly as Upkeep does. As built, `history.ts` filters the step's events to the moments E7-S2 names — a Party committed, returned, answered or turned back, an insistence, a Departure, an Injury, a Scar, a Death, a Hall improvement, a Transfer or a Poaching — together with the events `narrate` needs in order to tell them (`ApplicantAccepted` and `HeroJoined`, because a Transfer is told on the `HeroJoined` that closes it, DL-21 and E4 §4), and hands that list to `narrateEvents`. Every entry is therefore `narrate`'s own sentence, Day-stamped by the CLI and trimmed to two lines at the width in hand. Taking somebody on at the door comes along with the Transfers for that reason and is a decision in its own right, so the set is a superset of E7-S2's list rather than a subset.

    **Trimming to two lines is the one cut E7 sanctions, and it cuts at a sentence boundary where it can and a word boundary where it cannot** — never mid-word, and never with an ellipsis, which is forbidden everywhere else in the terminal. The entry is stored in the slot file at full length, so the same five entries reloaded at another width trim to that width rather than to the one they were saved at.

15. **Four sentences two front ends were already keeping identical copies of move into `narrate`.** `STANDING_EXPLAINED` (DL-22), `turnBackSentence` (DL-24 §A2b), the sentence that says another Guild could take a Hero (DL-22 §2) and the difficulty band above are all prose about the world, held word for word in `cli/src/display.ts` and in `web/src/state/selectors.ts`. E7's definition of done says all prose comes from `narrate`, so that is where they go; the web keeps its own selector names as pass-throughs, which is a one-line change each and leaves every web test and every Playwright check passing unmodified.

**Consequences.** The engine gains one config field and one re-export and nothing else. Every seeded expectation in the suite holds: `startingDebt` defaults to 0 and is subtracted in one place, `postingPatrons` is a re-export of a function the Board already called, and nothing in `narrate` that an existing test asserts is re-worded — the reckoning gains a line, and `narrate/tests/errors.test.ts`'s own case asserts the shape rather than the count, so it needed no edit for it.

`cli/src/display.ts`, `cli/src/index.ts` and `cli/src/saves.ts` are replaced by the module layout E7 §4 names — `main.ts`, `screen.ts`, `layout.ts`, `views/{roster,patrons,league,hall,former,applicants,rivals}.ts`, `commit.ts`, `word.ts`, `history.ts`, `slots.ts` and an `errors.ts` that is a re-export of `narrate`'s one map and nothing else. `cli/src/index.ts` survives as the three-line entry point `npm run play` and every spawned test already point at. Every test that was in `cli/tests/display.test.ts` and `cli/tests/saves.test.ts` moved with the code it covers rather than being deleted; the one pre-existing failure in the tree — `partyWaiting('display-refuse')`, whose seed deals a Commission no Decision can fire on since DL-24 §A3 narrowed their tags — is fixed the way DL-24 §A6 fixed the same class of breakage, by taking the first Commission on the Board that some Decision could actually stop rather than `board[0]`.

## DL-26 — E7 verification: the main screen is laid out inside a stated priority order it enforces, an awaiting Party the screen cannot hold whole becomes a loud summary and one named key, every confirmation moves out of the loop, and a history entry never ends mid-clause

**Status:** Accepted · **Date:** 2026-09-20 · **Decided by:** an agent, under the owner's standing instruction to build to the plan and to record what independent verification turns up. Every numbered item below is a decision taken in this change; nothing in it is an open question · **Amends:** [DL-25](#dl-25--the-e7-rules-as-built-the-starting-debt-is-an-opening-deduction-and-nothing-else-colour-is-applied-at-the-output-boundary-so-every-view-stays-a-pure-function-and-the-words-two-front-ends-already-shared-move-into-narrate) §14's trim rule, which §4 below supersedes. **A correction about the correction:** the builder's report of "25 rows on 2 of 37 seeds" was asked to be struck from DL-25, and it is not there — DL-25 makes no row-count claim anywhere, and the figure appears in no file in this repository. It was said and never written down, so there is nothing to correct in place; the measurement that replaces it is in the Context below, and the tick it misled is [E7](epics/E7-terminal-ui-and-saves.md) §1's E7-S1 acceptance box, which is corrected in this change together with E7-S2's trim box. DL-25 has not been accepted by the owner, so where it does carry a factual error it is corrected in place rather than left to mislead

**Context.** An independent verification of the built E7 measured `mainScreen` at 80 columns over **4,188 played states** from 60 Careers, bucketed by how many Parties were waiting on word: nobody waiting, 2,458 states, 64 over twenty-four rows (3%), worst 28; **one** Party waiting, 1,405 states, **1,217 over (87%)**, worst 39; two waiting, 294 states, all 294 over, worst 52; three waiting, 29 states, all over, worst 63; four waiting, 2 states, both over, worst 70. E7-S1's promise — "one screen, 80 columns, 24 rows, that a player can act from without scrolling" — is therefore broken for most of the screens a player who lets a word wait will ever see, and `cli/tests/layout.test.ts`'s "fits 24 rows" asserted it of **one** fresh-Career state. The same verification found that the five tests the E5 verifier forced in about the Transfer and Poaching confirmation had no equivalent after the restructure, because `moveConfirmLines` was inlined into `main.ts`; that the paid-Decision confirmation printed the option's raw id; and that at 40 columns every entry of the history stopped mid-clause.

**Decision.**

1. **The main screen has a stated priority order and a budget it enforces, and the order is part of the design rather than an accident of the order the blocks are concatenated in.** Four things are never given up, because E7-S1's own acceptance box names them: the header (the Guild, the Day, the Year, the coin and Standing), the Upkeep line with its two clocks, the Roster line, and the key hints. Everything else yields, in this order, and the screen is the **first rung of the ladder that fits twenty-four rows**:

   1. **RECENTLY** gives up its oldest entry, one at a time, until the block is gone. It is history: it is the one block holding nothing the player can act on from this screen.
   2. **The Applicants cue** collapses to one line naming the key that opens it.
   3. **The AWAY block** collapses to a one-line count naming the key that shows it whole.
   4. **The awaiting-Party block** gives way to the loud summary of §2, naming the key that shows it whole.
   5. **The AWAY one-line count** goes altogether, because the Roster line already says how many are away and `r` says where each of them is.

   Nothing is cut mid-sentence and nothing carries an ellipsis (E7-S5): a block appears whole, appears in a deliberately shorter **form**, or gives way to a one-line pointer naming the key that shows it. **The Board never yields.** It is bounded by `config.boardSizeMax`, and the numbers on it are the actions the screen exists for; a screen that hides the Board is not a screen a player can act from. Below 80 columns the layout is stacked and scrolls anyway (DL-25 §8, E7-S5), so the row budget does not run there at all — only §2's rule does.

2. **An awaiting Party is shown whole where the screen can hold it whole, and as a loud summary and one named key where it cannot; and that is the honest reconciliation of E6-S4 with twenty-four rows.** E6-S4 says an awaiting Party is "the loudest thing on the screen. The prompt, the options with their costs, and a single keypress to answer"; E7-S1 says it "displaces the Board as the top block and cannot be ignored". An authored prompt of six lines, three options with their costs, the turn-back sentence, a "cannot be sent" line and a three-line clock **per waiting Party** cannot be all of those things at once inside twenty-four rows, and the measurement above is what pretending otherwise looks like. So: where **exactly one** Party waits and its whole block fits the budget, the main screen shows it exactly as it showed it before. Otherwise — a prompt too long for the room, or **two or more** Parties waiting — the top block is a **loud summary**: who is waiting, on what Commission, how long they have waited and how many Days are left before they act on their own judgement, **soonest first**, and a line naming the key. It still displaces the Board and it still cannot be ignored; what it no longer does is pretend the screen has room for three prompts.

   **The key is `w`, and it opens the Word view** — `wordLines` in `cli/src/word.ts`, the same block, paged at twenty rows like every other view (E7-S3), where every prompt and every option appears whole and a single keypress still answers. The summary is therefore one keypress from the thing E6-S4 asks for, rather than a screen that has lost it.

   **Numbers answer only where the options are numbered in front of the player.** In the full form a number answers, as it did. In the summary form the options are not on the screen, so a number is refused with the sentence that says to press `w`, and the key hints read `[w] read and answer them` rather than `[1-9] answer them`. A key hint that is not true of the screen it sits under is worse than no hint at all. The guard is untouched: `n` is refused while anybody waits, the first `n` names who and for how long, and a second `n` lets the Days run (DL-23 §3, DL-24).

   §2's rule runs at **every** width, including below 80: the row budget does not apply there, but a 40-column player handed a seventy-row screen is no better served than an 80-column one.

3. **Every confirmation is a pure, exported, tested function of the engine's own selector result, and none of them lives in the loop.** `cli/src/confirm.ts` holds the Hall purchase, taking an Applicant on (the fee **and** the Upkeep their place adds), a Transfer, a Poaching, answering a Decision with an option that costs coin, and saving to a named slot on the way out. Each takes what a selector returned — `rivalOffers`' own `RivalHeroOffer`, `applicantOffers`' own `ApplicantOffer`, `wordOffers`' own `WordOption`, `hallCost` — and returns `string[]`, so a confirmation cannot reason for itself and cannot contradict the list the player has just read. The clause saying why a move cannot be made is **one function**, `whyNotMove`, shared by the list and by the confirmation, as it was before the restructure. The insistence confirmation stays in `cli/src/commit.ts`, which is where E7 §4 puts it and where it has always been pure and tested. This restores, by the behaviour asserted rather than by the title, the five tests the E5 verifier forced in after the CLI told the player the opposite of what the engine then did.

4. **A history entry never ends mid-clause, which supersedes DL-25 §14's "a word boundary where it cannot".** At 80 columns and above an entry is still the two lines E7-S2 sanctions, and it ends at a **sentence** boundary where there is one in range and at a **clause** boundary — a comma, a semicolon, a colon or a dash — where there is not. A cut at a plain word boundary is what produced "Year 2, Day 120 · Elswith Greyeye set out on The tithe barge down to" at 40 columns: no ellipsis, so the no-cut helper passed, and every entry stopped before the thing it was about to say. Punctuation is kept exactly as `narrate` wrote it — a clause cut ends on the author's own comma rather than on an invented full stop, because E7-S2 forbids the CLI to re-word an entry and inventing a sentence end is re-wording it. **Below 80 columns the Day stamp takes a line of its own and the entry is given the lines its first sentence needs**, because a sixteen-column stamp leaves about sixty characters of a 40-column pair of lines and sixty characters is not a sentence; the screen is stacked and scrolls there anyway, so room is the one thing it has. The entry is still stored **whole** in the slot file and trimmed at render time, so the width a Career was saved at never leaks into the file.

**Consequences.** `cli/tests/layout.test.ts`'s single-state "fits 24 rows" is replaced by a fleet: forty seeded Careers played under a policy that recruits, deals, buys the Hall and lets words wait, measured at 80 **and** 120 columns at every state they pass through, asserting every one is inside twenty-four rows **and** that the fleet actually saw each bucket — nobody waiting, one, two, three or more, a state where a block yielded, a state where the whole word block was shown and one where the summary was — so it cannot pass vacuously. The sweep gains an assertion that no rendered line over the fleet carries an identifier drawn from the engine's or the content's own id sets. `main.ts` loses every confirmation it was writing and the raw option id it was printing. No engine file, no `narrate` file and no content file changes.

10. **The browser shows every waiting Party whole, and deliberately does not copy DL-26 §2.** The terminal shows a **summary** when two or more Parties wait, and refuses a number on that screen, because twenty-four rows cannot hold three prompts and because a number would be ambiguous there. Neither reason exists in a browser: the pane scrolls, and every option is a labelled button tied to its own Party, so a tap can only ever mean one thing. Copying the summary would take information away from a screen that has room for it. 11. **The cross-front-end narration test lives in `web/tests/`, and loads the terminal's renderer by file URL.** ESLint forbids `web` from importing `cli` and `web/tsconfig.json`'s `rootDir` makes a static cross-package import a compile error; both boundaries are real and stay. `web/tests/save-interop.test.ts` had the same problem for DL-02 and solved it by loading the terminal's module through its file URL at run time, and this follows it, in the same place and for the same reason: the browser's reducer is bundled by Vite and only this project's Vitest configuration can load it at all. 12. **200% browser zoom is emulated as a halved CSS viewport at twice the device pixel ratio, because that is what it is.** Chromium implements zoom by changing how many CSS pixels the window is worth and raising `devicePixelRatio` to match, so a 1280×800 window at 200% is a 640×400 CSS-pixel viewport and **every media query re-runs at 640px**. A Playwright context at `viewport: 640×400, deviceScaleFactor: 2` reproduces both numbers a page can observe. CDP `Emulation.setPageScaleFactor` is **pinch** zoom — it leaves the layout viewport alone, no media query re-runs, and the check would pass without testing anything — and a CSS `zoom` or `transform: scale()` on the root has the same flaw. `Emulation.setDeviceMetricsOverride` with the same two numbers would be equivalent; the context is the same emulation through the door Playwright supports directly.

13. **DL-25 §12's claim about SIGINT on Windows was wrong and is corrected in place, not superseded.** DL-14 to DL-26 are uncommitted and unaccepted by the owner, and DL-26 already set the precedent of correcting a factual error in place rather than leaving it to mislead. Delivery of a real Ctrl-C **is** provable on this machine, by hand and with no new dependency: a PowerShell sharing the child's console calls `kernel32!SetConsoleCtrlHandler(NULL, TRUE)` to deafen itself and then `kernel32!GenerateConsoleCtrlEvent(CTRL_C_EVENT, 0)`. What is true, and is now what both DL-25 §12 and E7-S4's box say, is that it is **left out of the automated suite** because it needs the runner to share and deafen a console, which would take a Vitest run down with the child.

14. **The engine says plainly that a document carries no format version when it carries none.** `deserialiseCareer` said "it is format version undefined", which names a JavaScript value rather than anything a person can act on, and both front ends showed it. The code is unchanged and the refusal is unchanged; only the sentence is, and only in the branch where the field is absent.

**Consequences.** `narrate` gains one module (`history.ts`), two number functions, three sentences and the history's shared half; `cli/src/history.ts` and `cli/src/screen.ts` become re-exports of what moved, and every CLI test passes unmodified. Measured at the end of the change: **1,606 tests passed and 5 skipped across 88 files (2 files skipped), in about 180 s**, **141 checks passed, 47 per project, against the built bundle**, and **94 screenshots** under `docs/verification/`.

## DL-29 — E8-S7: a launcher executable that serves the built page on the loopback address, made with Node's own single-executable support and no new dependency

**Status:** Accepted · **Date:** 2026-09-20 · **Decided by:** the owner asked for "a script to build that creates an executable that launches a web server to enable play in the browser"; an agent chose everything below that sentence · **Amends:** [E8 §0](epics/E8-web-front-end.md#0-what-lands-in-e8)'s "Deliberately deferred: any server", which is narrowed to mean hosting

**Context.** Playing in the browser today needs a checkout, `npm install` and `npm run dev -w web`. E8 §0 and E8-S1's first box say the alternative is that "`npm run build` produces a folder you can open". **Measured on 2026-09-20, that is not true in Chromium**: Vite writes `<script type="module" crossorigin>`, and Chromium refuses a module script from a `file://` origin ("blocked by CORS policy: Cross origin requests are only supported for protocol schemes: chrome, chrome-untrusted, data, http, https"). `web/dist/index.html` opened from the filesystem in Playwright's Chromium renders an empty `#root`. So the built page needs *an* HTTP origin, and nothing in the repository provides one outside the development tooling.

**Decision.**

1. **`npm run build:exe` builds the page and then a single executable, `web/release/heroesim.exe` (no `.exe` off Windows), that holds the page and serves it.** It is a Node single-executable application made by `node --build-sea`, which copies the running `node` binary and injects the launcher script and every file under `web/dist` as an asset. No dependency is added, nothing is downloaded, and no `postject`. `--build-sea` arrived in Node 25.5, so **this one script needs Node 25.5 or later and says so in a sentence if it is run on less**; `engines` stays `>=22`, because nothing else in the repository needs more.
2. **The launcher is one zero-dependency file, `web/launcher/serve.mjs`, and it is the same code inside the executable and outside it.** Inside, it reads the page from the embedded assets (`node:sea`); run as `node web/launcher/serve.mjs`, it reads `web/dist` from disk. Either way every file is loaded into a map once, and a request is answered by looking its path up in that map — there is no path arithmetic on a request, so there is nothing to traverse. `GET` and `HEAD` only.
3. **Invariant 9 is read as it has been read since E8-S5: the loopback address is not "the network".** Playwright already plays the built bundle from `vite preview` on `127.0.0.1`. The launcher binds `127.0.0.1` and nothing else, so no other machine can reach it, and it makes no outbound request of any kind. The page it serves is the same bundle `check-bundle.mjs` has already passed. E8 §0's deferred "any server, any hosting, any account" was about running cost, and this has none.
4. **The port is fixed — 4790 — because `localStorage` belongs to an origin and the port is part of the origin.** A launcher that took any free port would show the player an empty slot picker every time it started. `--port` exists and warns that saves made on another port will not be there. If the port is taken, the launcher asks it who it is (`GET /__heroesim`): if it is another copy of itself — the player double-clicked twice — it opens the browser at the copy already running and exits; if it is anything else it says so and names `--port`.
5. **It opens the default browser unless told `--no-open`,** with the operating system's own opener (`cmd /c start`, `open`, `xdg-open`). If that fails the address is already printed.
6. **The executable is not committed and not signed.** `web/release/` is gitignored. It is roughly the size of `node` itself (about 95 MB on Windows x64). An unsigned executable built on the machine that runs it starts without complaint; one copied to another Windows machine may meet SmartScreen, and signing needs a certificate, which is a paid thing (invariant 9).

**Consequences.** One new story, E8-S7, in the E8 epic. New files: `web/launcher/serve.mjs`, `web/scripts/build-exe.mjs`, `web/tests/launcher.test.ts`. The engine, content, `narrate`, the CLI and `web/src` are unchanged, and the bundle is byte-for-byte what `npm run build` already made. **Not decided here, and raised for the owner in E8 §6.2:** whether E8-S1's "opens from the filesystem" box should be made true (dropping `crossorigin` is not enough — a module script is refused from `file://` with or without it — so it would mean a non-module build) or reworded now that the launcher is the supported way to open a build.

## DL-30 — Hosting: the built page is published to Cloudflare Pages as a static upload, on the free plan, with no build running on Cloudflare

**Status:** Accepted · **Date:** 2026-09-20 · **Decided by:** the owner asked what the most cost-effective way to host the app is, then asked to be walked through a build on Cloudflare and named the project `heroesguildsim-poc`; an agent chose everything else below · **Amends:** [E8 §0](epics/E8-web-front-end.md#0-what-lands-in-e8)'s "Deliberately deferred" list, both the "any server, any hosting, any account" bullet — already narrowed once by DL-29 — and the "Publishing to GitHub Pages" bullet

**Against convention, this entry was written after the deployment, not before it.** The owner asked to be walked through the deploy and the agent did so without stopping to record the decision first, as the log header requires. Recorded here so the record is complete rather than tidy.

**Context.** DL-29 gave the built page an HTTP origin on the machine that runs it, and read E8 §0's deferred "any server, any hosting, any account" as being about running cost. That left the page reachable only by someone holding a 95 MB executable or a checkout. E8 §0 also deferred publishing to GitHub Pages, citing INPUTS 8b.3's default of no. The question asked on 2026-09-20 was which hosting costs least, and the answer turns on what the page actually needs: `web/dist` is three files — `index.html` at 569 B, one JavaScript bundle at 420,754 B and one stylesheet at 8,456 B — and `web/scripts/check-bundle.mjs` has already refused any `fetch(`, `XMLHttpRequest`, `node:` specifier, `process.env` or unlisted URL literal in them. There is no server to host, no API, no database and no session. `vite.config.ts` sets `base: './'`, so the same folder works at a domain root or under a path without rebuilding.

**Decision.**

1. **Cloudflare Pages, free plan, at `https://heroesguildsim-poc.pages.dev`.** Chosen over GitHub Pages because `talonegg/heroesim` is private and Pages from a private repository needs a paid GitHub plan, and over Netlify because Cloudflare's free plan does not cap bandwidth where Netlify's caps it at 100 GB a month. Both alternatives would also have served this page adequately; the deciding factor was that Cloudflare asks for neither a public repository nor a card.
2. **The folder is uploaded already built; Cloudflare runs no build.** `npm run build` runs here, `check-bundle.mjs` gates it here, and `wrangler pages deploy` uploads the three files that passed. Cloudflare is given no repository access, no source and no build command. This keeps the bundle that is published byte-for-byte the one the gate approved, and it makes the free plan's 500-builds-a-month quota irrelevant because none of it is used.
3. **`--branch main` is passed explicitly on every deploy.** Wrangler infers the branch from git, the working branch is `feature/poc`, and the project's production branch is `main`. Without the flag a deploy becomes a preview that never claims the production subdomain. This is a flag that fails quietly rather than loudly, which is why it is written into the script rather than left to memory.
4. **Wrangler is not a dependency of this repository.** The deploy script calls `npx -y wrangler@4`, pinned to a major version. Adding a deploy tool and its tree to `devDependencies` would put roughly a thousand packages into the lockfile of a repository whose tests, engine and front end need none of them, to serve a command run by one person occasionally. Nothing in `npm install`, `npm test`, `npm run build` or CI touches wrangler.
5. **Invariant 9 is read as: the *app* reaches no service, and hosting costs nothing.** The page published makes no request of any kind — the same bundle check that DL-29 §3 relied on still passes — stores its saves in `localStorage`, and needs no account from a player. What is new, and is stated plainly rather than folded into the old reading: **this repository's owner now holds a Cloudflare account, and hosting is an external service in the delivery path.** It has no running cost and no paid tier is used. No credential enters the repository: wrangler's OAuth token lives in its own configuration directory under the user profile, outside the checkout, and the project name in the deploy script is a public subdomain, not a secret.
6. **The page is public and unlisted rather than gated.** Anyone with the URL can play; nothing links to it. Cloudflare Access could restrict it to one email on the free plan and was offered and not taken, on the grounds that a proof-of-concept nobody has been given the address of does not need a login in front of it.

**Consequences.** `npm run deploy` at the repository root builds and publishes in one command; `web/package.json` gains the `wrangler pages deploy` invocation it delegates to. No source file, test, engine behaviour or bundle content changes, and `npm test`, `npm run typecheck` and `npm run lint` are untouched by this entry. Two E8 §0 bullets gain an amendment note pointing here, in the style DL-29 already used.

Measured at the time of writing: the three files uploaded in 2.51 s; `https://heroesguildsim-poc.pages.dev/` answered 200 with the expected `index.html`, the bundle 200 as `application/javascript` and the stylesheet 200 as `text/css`; and Cloudflare served the bundle compressed at **126,742 B**, against 420,754 B on disk. The per-deployment hash URL did not resolve for about a minute after the deploy while its subdomain propagated, which is expected and affects only that URL, never the production one.

**Two things a later reader should not have to rediscover.** First, `wrangler pages project create` now delegates to "the latest version of Cloudflare Pages, now part of Cloudflare Workers", which refused to run from the workspace root and then, from `web/`, detected this application as **Hydrogen** — Shopify's Remix framework — and proposed to build it with `npx remix vite:build`. The detection is simply wrong and there is nothing here to configure, since the folder is already built. `--force` takes the direct path that uploads a folder. Per Cloudflare's own message this is needed **only once, to create the project**; the project now exists, and passing `--force` on later commands is not required. Second, this is an external service whose plans and limits are outside this repository's control: the free-tier terms relied on in §1 were read on 2026-09-20 and should be re-checked rather than trusted from this entry if the cost ever matters again.
