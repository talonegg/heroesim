# v1.1.9 — The tests and the harness made faster and leaner, the design unchanged

**Objective:** make the test suite, the harness and CI faster, and the tests leaner, without changing
play or weakening the architecture or what the tests protect. Four read-only analyses of
2026-10-09 (§5) found that:
- a full local `npm test` takes 119–126 s, and most of that is contention between tests that start
  processes and browsers, not the tests themselves;
- half of every harness game is quest estimation, the Rivals' and the policy's;
- CI bills 22–44 minutes a push, `npm test` running twice in it and three times in a release;
- about 400 tests across the packages are duplicate, suspected redundant, tautological or slower than
  their assertion needs.

The owner's answers to Q1–Q30 (§6) set the scope, and DL-231 records them.

**Sessions:** 13–17 (agent's estimate) · **Depends on:** `v1.1.8` released (pull request #59, merged
as `10f17aa`) · **Implements:** DL-231.

**Gate** (Q30):
- *Play unchanged.* A story that keeps the save's format shows an identical `neutral` fingerprint
  (`neutral --expect`). A story that changes the format shows 0 play counters moved in `compare` and
  records a new baseline in its DL entry (Q2). At the close, a full `gate` meets `harness/gate.json`
  and the engine's twenty-year boxes pass (DL-230).
- *The design holds.* The ADRs hold as written or as amended. Each amendment keeps its decision's
  intent, is dated in the ADR with a DL entry, and has the owner's word (Q14).
- *The tests hold.* Three full `npm test` runs in a row pass without a failure. Every test removed was
  approved by the owner in its package's batch (Q3) and shown redundant by Q9's evidence.
- *Coverage.* Lines and branches per package are no lower than S1's baseline, or each drop is
  explained in its DL entry and accepted by the owner at the close.
- *Every check.* `npm run lint`, `typecheck`, `test`, `build` with check-bundle and `e2e -w web`
  pass; `npm run edit -- traits doctor` reads no drift before and after each story that touches
  `engine/src/` or `content/src/validate.ts`.

There are no numeric targets (Q17). Before and after are measured locally, in CI minutes, and for
the `gate` and `neutral` runs; the game's figures are reported only (Q1, Q21).

**Status:** Planned 2026-10-09 from the analyses (§5) and the owner's answers (§6, DL-231);
`v1.1.9-dev` cut from `26cd276` and Dependabot moved to it on the owner's word ("do all 3 next steps,

### v1.1.9-S2 · The suite's structure · 1.5–2 sessions · opus

- *Contention* (Q23). The tests that start processes or browsers go in one Vitest project with
  limited concurrency, and the pure tests stay fully parallel. These are:
  - the editor's "Finish" and page tests;
  - the portrait tool's Chromium tests;
  - `bundle.test.ts`;
  - the boundary tests that spawn lint;
  - the scans of every file in the repository.

  Their counts are cut in the same story:
  - one shared browser;
  - a stub for most "Finish" tests, with one kept end to end;
  - fewer bundle builds.
- *Environments.* The 20 `web/src/state/*.test.ts` files run in Node, as the 12 top-level files
  already do.
- *The owner's pictures* (Q15). `tools/portraits/src/owner.test.ts` runs only when
  `HEROESIM_OWNER_PICTURES` is set; `docs/environment.md` and the portrait skills say so.
- *The CLI's tests.* A test-support module. Fewer files import `main.ts`, and the cycle from
  `recruit.ts` to `main.ts` is removed.
- *Transforms.* Vitest's transform cache, and isolation where a project's tests share no state.
- *`withValid`* (Q26). It passes `historyFrom`, so a test game still validates every Turn but
  re-reads only the History's new entries.

**Acceptance:**

- [ ] Three full `npm test` runs in a row without a failure; time per project before and after.
- [ ] Every test that ran before still runs, in `npm test` or in a named run apart; the counts match.
- [ ] `withValid` red on a planted fault in an earlier History entry that the full check found, if

### v1.1.9-S7 to S10 · Pruning, one batch per package · 1–1.5 sessions each · sonnet, verified by opus

Each batch runs the same way (Q3, Q9):
1. Its candidates are re-derived at the batch's commit, starting from §5. Each candidate gets a
   kind, its evidence and an Opus verdict.
2. The owner approves or strikes the list.
3. The approved list is applied.
4. Opus verifies each removal of a redundant test. Coverage per test shows the candidate covers

5. Coverage per package is reported against S1's baseline.

- *Pins of a default* (Q10): removed. A test whose numbers merely rest on a default stays.

  stays.
- *Story ids* (Q16, Q27): out of test names and comments. Tests come under the citation ratchet.
- *Slow tests:* fewer seeds, Turns or worlds, where the assertion still shows its property.
- *Shared fixtures:* a shared game is never played forward (ADR-0008).
- *Helpers:* repeated helpers move to the package's test-support module.

## 4. Risks

- *A faster engine that plays differently.* Every engine story is proved by `neutral --expect`,
  alone. A cache that misses an input changes a Rival's choice and the fingerprint.
- *Pruning that weakens the tests.* Q9's evidence, the owner's batches and the coverage review
  (Gate) each guard against it. Acceptance boxes shrink or move; they are never deleted.
- *Moving tests out of `npm test`.* The speed assertions and the dispositions box move to runs
  apart that only a close plays (Q7, Q22, Q25). The Gate's close runs every one.
- *Contention measured on one machine.* Local timings vary by several seconds. S1 takes each
  baseline twice, and S11 measures after the same way.
- *The research's lists go stale.* The candidates in §5 come from `26cd276`. S2–S6 move code, so each
  batch re-derives its own list (S7–S10, step 1).

## 5. The analyses' findings (2026-10-09)

Four read-only analyses of the repository at `26cd276`. One measured, running each command alone.
Three read the tests of the engine, of web, cli, words and content, and of the harness and tools.

**The suite.**
- *Totals.* 231 files and 6,102 tests, 119–126 s wall. Of that time, tests are 67–69%, import 16%,
  transform 9–10% and environment 6–7%.
- *Contention.* Each project run alone, one after another, totals 207 s, so running them together
  gains only about 1.7×:
  - the editor's page test takes 2.4 s alone and 41 s in the full run;
  - `cli`'s transform takes 13.5 s alone and 48–53 s in the full run.
- *Where test time goes.* The tests add up to 1,748 s. Half of it is in 98 tests, and 4,663 tests take
  under 0.1 s each.
- *The slowest tests:*
  - `harness/src/write-once.test.ts`, 72 s;
  - the editor's page test, 41 s;
  - `owner.test.ts`, 38 s and the local run's tail;
  - the portrait tool's convert, 30 s;
  - the web reducer's year of steps, 24 s;
  - the engine's world-copy, 23 s;
  - dispositions, 22 s.
- *The bundle test.* `bundle.test.ts` runs 5 `vite build`s, 40–46 s; one build takes 1.8 s.

**Coverage** (v8, 2026-10-09).
- *Overall.* Lines 97.7%, branches 88.2%.
- *Per package.* The engine 99.8% / 95.4%; `cli` 95.2% / 82.2%; the portrait tool 95.3% / 76.4%.
- *Untested.* Only the five entry points are uncovered.
- *Caveats.* Code run only in child processes is not counted. 5–19 tests fail under coverage, all of
  them timing tests.

**One game** (20 years, alone, profiled).
- *Totals.* 89.6 s, with a peak of 1.3 GB.
- *Where the time goes:*
  - the quest estimate, 48.7%, of which the Rivals' choice of a Party is 42% of the game;
  - `copyWorld`, 16.1%;
  - the policy, 13.5%;
  - `applyAction`, 6.4%;
  - the yearly walk of the document, 5.4%;
  - the end-of-game checks, 6%.
- *By year.* The cost peaks in years 10–11, following the Heroes in play.
- *In the Engine's Turn code.* No pattern that grows quadratically over the History.
- *In the tests.* `withValid`'s missing `historyFrom` makes long test games quadratic.

**The `gate`** (v1.1.8, 1,423 s).
- *Shares.* Play 78%, the checks within each game 11–13%, the replay alone 6%, and process starts
  4.5%.
- *Workers.* A game is 2.4× slower with 8 at once, so 8 workers give about 3.3× one's throughput.

**CI** (private, billed).
- *Per push.* 22–44 job minutes a push, at about 7.7 runs a day. `npm test` is 85–92% of each job.
- *The two Node versions.* `npm test` runs on both, and the Node 22 job is about 2× slower.
- *A release.* It runs the suite and e2e three times on the same tree.
- *e2e.* 241–273 s on one worker, of which `layout.spec` is 113 s.

**The game.**
- *A year's fast forward.* 3.16 s, against the recorded target under 1 s.
- *A save's load.* 1.46 s alone, against under 1 s.
- *The bundle.* 827,430 bytes, at 97.3% of its limit.

**The tests** (candidates at `26cd276`, about 400 in all):

| Kind | Engine | Web, cli, words, content | Harness, tools |
|---|---:|---:|---:|
| Duplicate | 18 | about 38 | 7 |
| Redundant (suspected) | 41 | about 24 | 5 |
| Tautological, pins included | 34 | about 25, and about 35 content pins | 8 |
| Slow without need | 42 | about 24 | 9 |

The strongest examples:
- *The narration.* Each event's sentence is pinned in `words`, in the page's namer and in the CLI's.
  Three tests are verbatim copies between the two front ends.
- *Content.* `refusals.test.ts` reads all 21 content files about 8,400 times. About 84 of its
  refusal cases repeat `query-refusals.test.ts`.
- *Engine.* `create.test.ts:529` creates 2,000 worlds where about 100 would show the property. The
  "copy equals in place" test is written six times.
- *The pictures.* `owner.test.ts` runs in every local run. 39 portrait tests each build a git
  repository.
- *Pins.* `gate.test.ts:43` copies `gate.json`'s baseline. `registry.test.ts:71` pins 40 picture
  keys.

*Keep but note* (these protect a deliberate rule):
- the fingerprint pins;
- stream isolation and draw counts (ADR-0009);
- sharing by reference (ADR-0008, ADR-0011);
- the lint and boundary tests;
- the validator's rows;
- the capitals guard and the credential scan;
- the bundle gate and the accessibility walks;
- data-model rule 9's tests;
- every acceptance box.
